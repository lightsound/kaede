# ADR: RealtimeKit 参加トークンの有効期限を24時間に明示する

- **ステータス**: **採用（2026-11-27 確定）** — PR #200 のレビュー指摘（判断記録は
  コードコメントではなく ADR に置く）を受けて本 ADR に記録
- **対象**: kaede の通話（packages/server の RealtimeKit 参加トークン発行）
- **最終更新**: 2026-11-27

---

## 1. 決定

**RealtimeKit の参加トークンの有効期限を、発行時に24時間と明示する。**

プロバイダのデフォルトは100日であり、参加トークンはクライアントがプロバイダに
提示する唯一の資格情報であるため、発行した勤務日の2桁も先まで生き続ける
チケットにしない。

---

## 2. 仕組み

参加トークンは Add Participant（`POST /meetings/{id}/participants`）で
参加のたびに発行する。そのリクエストの `token` フィールドで有効期間を
ISO 8601 文字列のペアとして渡す。

- `not_before`: 発行時刻から60秒遡った時刻（→ §4）
- `expires_on`: 発行時刻の24時間後

発行時刻はプロシージャ自身のタイムスタンプ（`nowMs`）を正とする
（listRecordings の時刻源ルールと同じ）。実装は
`packages/server/src/provider.ts` の `mintParticipantToken` で、
定数は `PARTICIPANT_TOKEN_TTL_SECONDS`（86,400秒）。

---

## 3. 24時間が安全な理由

- **クライアント SDK はトークンをリフレッシュしない**。リフレッシュは
  バックエンド専用 API であり、kaede はどのみち参加のたびに新しい
  トークンを発行する。有効期間は長い勤務日の再参加までを単独で
  カバーしなければならない。
- **再参加は再発行で賄える**。期限切れが効くのは次の参加時だけであり、
  その参加は `join_group_call` 経由で新しいトークンを発行し直す。
- **接続中の参加者は期限切れで切断されない**（プロバイダ FAQ）。
  したがって有効期間の境界で進行中の通話が落ちることはなく、24時間は
  「長すぎず、通話を殺さない」長さとして成立する。

---

## 4. not_before の60秒のずれ許容

`not_before` は発行時刻ちょうどではなく、60秒前倒しする
（`TOKEN_NOT_BEFORE_SKEW_SECONDS = 60`）。

発行時刻の正は SpacetimeDB ホストの時計だが、トークンの検証はプロバイダ側の
時計で行われる。ホストの時計がプロバイダより進んでいると、`not_before` が
プロバイダ側の「未来」になり、参加が「まだ有効でない」として拒否されうる。
60秒の前倒しはこの時計ずれを吸収するためのもので、有効期間の実質的な
延長（24時間に対する60秒）は無視できる。

---

## 5. 判断が覆る条件（見直しトリガー）

以下のいずれかが真になったら、この ADR を再評価する。

1. **クライアントがトークンリフレッシュを持つようになった** →
   有効期間は「勤務日をカバーする長さ」である必要がなくなり、
   より短い期限（時間単位）へ締め直す
2. **プロバイダのデフォルトや `token` フィールドの仕様が変わった** →
   §2 の仕組みごと再確認する
3. **参加拒否や期限切れ起因の参加失敗が実測された** → §4 のずれ許容の
   幅を含めて再検討する
