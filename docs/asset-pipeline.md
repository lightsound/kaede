# kaede アセット規格とファクトリー（全アセット共通）

状態: **設計確定（2026-08-08 オーナー承認）**。適用範囲は **kaede の世界に
出る絵のすべて** — アバター（体・頭・髪・顔）、装備・手持ちアイテム
（剣・パソコン等）、オブジェクト（マスコット・家具 — Phase 4.5 増分⑦）、
背景（タイル・パララックス層）。アバターの**動かし方**（ポーズ規約・
アニメ・着せ替えの層構造）は [docs/avatar-rig.md](./avatar-rig.md)、
増分の分割と順序は [ROADMAP Phase 5](./ROADMAP.md)。

## 0. 三つの構想（本規格の憲法 — オーナー 2026-08-08）

1. **世界観の統一感**: いろんなデザインが混ざると統一感が失われ、
   プロダクト自体の魅力が失われる。統一感を**仕組みで**守る（§3）。
2. **販売可能性**: 統一感を持ったアセットはそれ自体がプロダクトになり得る
   （VISION の Phase 6 通貨・課金と接続）。
3. **ユーザー制作（UGC）**: 将来、ユーザーが自社ロゴの T シャツや
   マスコットを持ち込める仕組みへ。マーケットプレイス化も視野。

2・3 は**最初から実装しない**。ただし「やりたくなったときにできる」ための
不変条件（§5）を全増分が守る。

## 1. 資産の正はエンジン非依存（kaede ファースト）

- アセットの**正（source of truth）は透過 PNG ＋ manifest JSON**。
  グリーンバックの生成原本も保存する（再生成・派生生成の素材）—
  ただし置き場所は Git ではなく R2（§4「原本の置き場所」— ①b⑶）。
- **PixiJS は再生機**にすぎない。ツール固有形式（Spine プロジェクト・
  Live2D モデル等）をソースにしない — ポーズフレーム方式
  （avatar-rig.md §2）はこの点でロックインが構造的に最小。
- アトラス（配信用に画像を 1 枚へ詰めたもの）は**ビルド時の派生物**
  （Pixi 公式ツール AssetPack）。正は常に個別 PNG ＋ manifest に残る。
- これは「マルチエンジン対応をする」話ではない。kaede 本体が唯一の
  再生対象で、**正を汎用形式に保つだけ**（追加コストゼロの習慣）。
  販売（§0-2）・UGC（§0-3）はこの習慣の上に乗る。

## 2. kaede アセット規格 v1

### 種別

| 種別 | 実体 | アニメ | 備考 |
| --- | --- | --- | --- |
| `avatar-body` | ポーズシート（全身コマ群） | コマ切替 | ポーズ規約は avatar-rig.md §3 |
| `head-group` | 頭・髪・顔（表情）の 1 枚絵 | なし（体コマの neck アンカーに合成） | 着せ替えの主戦場 — 爆発しない |
| `held-item` | 手持ちアイテム 1 枚絵（ポーズ限定可） | なし（hand アンカーに合成） | 剣・PC・コーヒー等 |
| `object` | 静的 1 枚絵（関節なし） | なし（将来: コマ切替可） | 増分⑦の装飾・機能オブジェクト |
| `background` | タイル・パララックス層 | なし | 増分⑦段階①に統合済みのマップアート |

### manifest スキーマ（共通フィールド）

```jsonc
{
  "id": "avatar.boy-basic",        // 安定 ID（不変・ファイル名ではなく ID が正）
  "type": "avatar-body",
  "name": "男の子（基本）",
  "author": "kaede",               // UGC 期にユーザー ID が入る
  "license": "kaede-internal",     // 販売・UGC 期のライセンス識別子
  "palette": ["#8a5a2b", "…"],    // 主要色（アート lint の検査対象）
  "source": {                       // 再現性: ファクトリーの発注書を記録
    "prompt": "…",
    "referenceHashes": ["…"]       // 使った基準リファレンスのハッシュ
  },
  // 種別ごとの追加フィールド:
  "poses": { "stand": {...}, "walk-a": {...} },  // avatar-body のみ
  "anchors": { "neck": [x, y], "hand": [x, y] }   // コマごと（avatar-rig.md §3）
}
```

- **解像度は表示の 2 倍**（Phase 4 の前例を全種別に適用）。
- 種別ごとのキャンバス・頭身規約は数値で定義し、アート lint（§3-3）が検査
  する。
- `id`・`author`・`license`・`source` を**最初から**持つのは §0-2/3 の
  ための不変条件（後付けすると全 manifest の作り直しになる）。

## 3. 統一感の 4 層機構

スタイルガイドを「人間向けの注意書き」から「機械が強制できる仕組み」へ
格上げする。

1. **基準リファレンスセット（canonical）**: 「kaede の絵柄」を定義する
   正典画像（基準キャラ・基準パレット・基準オブジェクト・基準背景）を
   リポジトリに置き、**すべての生成に参照画像として必ず渡す**。生成 AI の
   出力を揃える最も効くレバーは言葉ではなく参照画像。
2. **機械可読な規格**: §2 の manifest スキーマ＋種別ごとの数値規約
   （寸法・頭身比・アンカー）。
3. **アート lint（取り込み時の自動検査）**: 取り込みスクリプトが寸法・
   頭身比の範囲・パレットからの色距離・背景（クロマキー残渣）の純度・
   アンカーの存在を機械検査し、規格外は取り込み失敗にする。アンカーは
   「テンプレート側の目標座標 vs 生成結果からの実測座標」の乖離を自動計測
   して閾値超えをフラグする形へ拡張する（2026-08-08 外部レビュー採用 —
   ずれたら再生成、の判断を機械化する）。
4. **オーナー承認ゲート**: 最終の「かわいいか・世界観に合うか」は機械化
   しない。**アセット追加は必ずシート画像が見える PR** で行い、オーナーが
   目視承認する（「見た目の変更はオーナー確認が完了条件」— Phase 4.5 で
   確立した規約のアセット版）。

## 4. ファクトリー（量産ライン）

**オーナー方針（2026-08-08）: ここに最も力を入れる。** アセット生成の品質と
運用の楽さは、ラインの整備度で決まる。目標状態は「**コードを書かずに、
発注書を書けばアセットが増える**」。

### ラインの工程（全種別共通）

```
①発注書        種別・名前・意図＋種別別プロンプトテンプレ＋基準リファレンス
   ↓
②生成          グリーンバックのシート（ポーズシート / 1 枚絵 / タイル）
   ↓
③取り込み      クロマキー → 切り出し → 規格サイズへ正規化 → manifest 生成
   ↓
④アート lint   寸法・頭身・パレット・残渣・アンカーの自動検査（不合格は差し戻し）
   ↓
⑤アトラス化    AssetPack で配信用アトラスへ（ビルド時派生物）
   ↓
⑥PR            シート画像が見える PR → オーナー目視承認 → マージ = 配信
```

- **全種別が同一ライン**: アバターのポーズシートも、⑦の装飾オブジェクトも
  背景タイルも、違うのは「テンプレと規格の数値」だけ。工程・スクリプト・
  検査・承認フローは共通。
- **再現性**: 発注書（プロンプト・参照ハッシュ）を manifest の `source` に
  記録する。再生成・色違い等の派生生成・将来の UGC 翻訳（§5）が同じ
  発注書形式に乗る。
- **原本の置き場所（①b⑶ — 2026-08-09）**: 生成原本・ボツ案は Git に
  入れない（原本 1 枚 300KB〜1.3MB vs 取り込み結果 60KB — 再生成のたびに
  clone が永久に肥大する）。`*-original.png` は gitignore され、
  `scripts/upload-asset-originals.py` が R2 バケット
  `kaede-asset-originals`（Alchemy IaC — infra/alchemy.run.ts。**名前は
  stagedName しない** — 録画と違い git ファクトリー共有の一点物）へ
  **内容アドレス**（key = `originals/<sha256>`。論理ファイル名・拡張子は
  key に含めない）で保存する。CLI 引数は
  シードで、ディスク上の原本を 1 回 PUT したあと、同じファイルを指す
  **全**発注書の `originals` マップ（発注書相対パス → sha256）を書き換える
  （`sheet-original.png` と `../avatar/sheet-original.png` は resolve で
  同一 — 共有参照の再記録を運用に頼らない）。取り込みスクリプトは
  ローカルに無い原本をこのマップ経由で取得し、sha 照合してから使う
  （改竄・取り違えは fail loud）ため、**再取り込みは常に committed
  manifest を byte 再現するか、大声で失敗するかのどちらか**。ローカルに
  居る原本が記録値と食い違う場合（アップロード前の再生成）も fail loud —
  先に upload-asset-originals.py をその原本を名指す**いずれか**の発注書に
  掛けると、共有する全 order のマップを更新し、影響する全 importer も
  自動再実行する（ローカル優先が無条件なのは未記録の初回生成だけ）。
  各 order は一時ファイルを format してから atomic replace する。
  ストアは追記専用（再生成は新キーを増やし、参照されなくなった旧原本は
  R2 に残る — 今の分量では実害なく、棚卸しツールは量産期に必要になったら
  足す）。Git に残るのは取り込み結果 PNG・manifest・発注書・
  基準リファレンス — オーナー承認ゲート（§3-4「シート画像が見える PR」）は
  取り込み結果 PNG がそのまま担い、不変。
  order にまだ採用していない生成候補・ボツ案は、発注書のポインタを
  作らずに `upload-asset-originals.py --file <asset-root-relative-path>`
  で同じ R2 ストアへ保管できる（CLI は asset root 外を拒否する）。
- **段階的整備**（増分対応は ROADMAP Phase 5）: ①a で最小ライン
  （既存のクロマキー取り込みスクリプトの拡張）→ ①b でテンプレ・基準
  セット・アート lint・manifest 生成を整備し「発注書だけでアセットが
  増える」状態を完成 → 以降の種類追加・⑦のオブジェクト・背景は
  **ラインの運転**であって開発ではない。
- **運転手順（①b 本体）**: 工程の接続・コマンド・歩留まり記録は
  [asset-factory.md](./asset-factory.md) / [factory-yield.md](./factory-yield.md)。
  入口は `scripts/factory/run_avatar.py`（テンプレ展開 → 生成 →
  足位置解析 → 頭部合成 → 取り込み → 構造ベース art lint）。アトラスは
  `pnpm --filter @kaede/client assets:pack`（AssetPack、派生物）。

## 5. 販売・UGC への不変条件と決定ポイント

### 全増分が守る不変条件（コストほぼゼロ）

1. **安定 ID**: アイテムの正は manifest の `id`。描画・所持・（将来の）
   価格はすべて ID を参照する。
2. **持ち物は account スコープ**: 誰が何を持つかは組織を跨いで持ち歩ける
   account に置く（VISION のガードレール。着せ替え増分のスキーマが土台）。
3. **アセット＝データ**: 種別・見た目・アンカーは manifest 駆動で、
   アセット追加にコード変更を要しない（§4 の目標状態と同義）。

### 決定ポイント（実施時期が来たら判断する。今は作らない）

- **DP-1 配信の R2 移行**: MVP はビルド同梱（Vite import）。販売・UGC を
  始める時点で「カタログ＝DB 行、画像＝R2」へ移行する（録画の R2 前例
  あり。同梱のままでは新アイテム追加のたびにデプロイが要る）。
- **DP-2 マーケットプレイス**: LINE スタンプ型の販売は、権利処理（商標・
  著作権）・モデレーション・決済手数料の**事業判断**が乗る。Phase 6 の
  SaaS 期に UGC 段階③（下記）とセットで判断。
- **DP-3 スタイル学習（LoRA — 2026-08-08 追加）**: 基準リファレンスセット
  （§3-1）を「参照画像を毎回渡す」から「承認済みアセットで学習した専用
  スタイルモデル」へ格上げする案（Scenario 等の専業 SaaS、または fal.ai
  BYOK のオープンモデル LoRA — 後者は AI Gateway 前段でログ・キー管理の
  Cloudflare 集約を保てるため比較の第一候補）。BYOK は統一課金の
  「プロバイダキー不要」からの一歩後退だが、fal キーは AI Gateway に
  保管させ（BYOK ストア）、呼び出しは常に `gateway.ai.cloudflare.com`
  経由にすることで、キーの置き場所・観測・レート制御は Cloudflare
  1 か所のまま — 増えるのは fal との契約だけ。**実施トリガー**: アート
  lint がスタイルドリフトを実測で検出したとき、または承認済みアセットが
  10 体規模に達して学習データとして意味を持ったとき。それまでは参照画像
  方式で十分（nano-banana-2 の参照忠実度で実証済み — 2026-08-08 ベンチ）。
  LoRA が解くのはスタイルでありポーズではない（ポーズの解は生成ベンチの
  採用ライン）。
- **DP-4 アバター工場の外販（2026-08-11 オーナーアイディア — 実施判断は
  後日）**: ハイブリッドレーン（画像 1 枚 → Meshy 3D リグ＋プリセット
  モーション → 動画モデルで 2D 清書 → ループ保証・アンカー付きスプライト
  シート一式）を「画像を渡すと 2D ゲームキャラ化」のサービスとして外販する
  構想。PR #98 のスパイクで技術成立は実証済み — 原価 1 キャラ＋動作
  10 本 ≈ $7〜9（約 1,000〜1,300 円）・所要 30〜60 分・全工程自動・
  振り付け決定論（ガチャなし）・キャラ間モーション転用可。ニッチは
  「ゲームでそのまま使える完成スプライトまで一気通貫」（3D 化単体や動画
  生成単体の既存サービスと重ならない）。**サービス化の前提課題**:
  ①ユーザー持ち込み画像の権利・モデレーション ②参照動画ホスティングの
  自前化（スパイクは外部一時ホスト経由 — 単一障害点）③検品の完全自動化
  （機械ゲートのみで出荷する品質割り切り）。**判断時期**: まず kaede
  自体のアバター量産で工場を回して実績・検品ノウハウを蓄積してから
  （Phase 6 SaaS 期に DP-2 マーケットプレイスと合わせて再訪）。

### UGC の段階（実施順の叩き台）

1. **静的オブジェクト**（自社マスコットの置物）: `object` 1 枚絵 —
   最も簡単で B2B 実需に直結。
2. **服へのプリント**（自社ロゴ T シャツ）: テンプレ服の決められた
   貼り付け領域にロゴを差し込む。ポーズ対応はテンプレ側が済ませている。
3. **フルアバター持ち込み**: ポーズシート一式の生成・検品が必要な最難関。
   DP-2 とセット。

**統一感との両立（本規格の核心）**: ユーザーの任意画像をそのまま置かせる
のではなく、**持ち込み素材を §4 のライン（基準リファレンス付き生成 →
アート lint → モデレーション）に通して kaede の絵柄へ「翻訳」する**。
統一感の機構（§3）がそのまま UGC の品質ゲートを兼ねる — AI 生成を
ラインの中心に据えた方式だからこそ成立する差別化で、手描きアセット文化では
成立しない。
