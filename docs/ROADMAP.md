# kaede — ロードマップ

前提: [VISION.md](./VISION.md) を先に読むこと。**品質優先・締切なし**。フェーズは
依存関係に基づく順序であり、日付ではない。各フェーズの完了時（および方針変更時）に
本ファイルを PR で更新する。

**移行ライン（oVice からの引っ越し条件）**: ログイン ＋ 常設マップ ＋ チャット ＋
ステータス ＋ ビデオ通話（画面共有含む）。= **Phase 4 完了がコミュニティ移行の
マイルストーン**。

アートのワークストリーム（AI 生成×パーツ分割の検証）はフェーズに縛られず
**並行して**進めてよい。本格統合は Phase 5。**ただし Phase 4 の移行までに
「最低限のアバター」（着せ替えなしの簡易キャラ 1 種）を投入することを必達目標と
する** — コミュニティの第一印象を「色付き矩形」にしないため。

## Phase 1: アイデンティティ基盤

**ゴール**: メンバーが複数デバイスから同じ名前・同じアバターで入れる。
メンバー以外は入れない。

- **最初のタスク: Clerk ↔ SpacetimeDB 接続スパイク** ✅ **完了（2026-07-30）**:
  実装に無理はなく、フォールバック（Kinde）は不要。検証内容: ①Clerk 開発
  インスタンスに JWT テンプレート `spacetimedb`（`aud: kaede-spacetimedb`、
  寿命 60 秒）を Backend API で作成 ②SpacetimeDB に issuer の事前登録機構は
  なく、モジュール側 `clientConnected` リデューサーで issuer＋audience を検証
  するのが公式ベストプラクティスと確認（実装済み） ③フレッシュトークンでの
  再接続 2 回で**同一 Identity** を確認（Identity は iss＋sub から導出）
  ④aud なしトークン（素のセッショントークン）はモジュールが拒否
  ⑤トークンなしのゲスト接続は従来どおり別 Identity で入れる。
  補足: ローカル standalone のサーバー発行トークン（匿名 Identity）の issuer
  は `localhost`。クライアントは接続試行のたびに `getToken({ skipCache })` で
  新トークンを取得する配線に変更済み

  形にした（`@kaede/shared` の `memberIssuersFor` — 単体テスト済み）。

  落ちる。それ以外のデータベース（ローカル standalone・E2E・ステージング）

  pk_test_ で進められる。ピン留めが古びると開発 issuer が本番で復活する

  `PRODUCTION_DATABASE_IDENTITY` のコメント参照）。クライアントの本番キー
  切替（CI deploy の `VITE_CLERK_PUBLISHABLE_KEY`）とモジュールの issuer

  issuer で手動サインアウトまで再試行が続くため — `onConnect` コメント）
  ② **未登録 issuer をゲストとして通す暫定措置をやめる** ✅ **完了
  （2026-08-02）**: Maincloud のサーバー発行トークンの issuer
  （`https://auth.spacetimedb.com` — 本番ログで実測）を `guestIssuers` に
  加えたうえで、未登録 issuer の接続は `clientConnected` で拒否に切り替えた

  購読 — 位置やメンバー一覧の読み取り — だけは可能で、ゲストの権限が
  増えるほど広がる穴だった）。拒否を join ではなく接続層に置いた理由と
  拒否されたクライアントの挙動（ゲストの保存トークンは連続失敗後に破棄

  するため手動サインアウトまで再試行が続く — ゲート①で issuer を
  差し替える際はクライアントとモジュールを同時デプロイすること）は

- **承認制（待合室）** ✅ **完了（2026-07-30、申請フロー改訂 2026-07-31）**:
  Discord 型の原則「アカウント（グローバルプロフィール）とスペースの
  メンバーシップを混ぜない」で設計。サインイン時に `account` を作成し、
  表示名は IdP のプロフィール名（JWT の `name` クレーム）で初期化
  （Clerk JWT テンプレート `spacetimedb` への `"name": "{{user.full_name}}"`
  追加は Backend API 経由で反映済み — 2026-07-31。`aud: kaede-spacetimedb` と

  `space_member` 行（公開テーブル）が `pending` になり、`join` をサーバー側で
  拒否。申請中クライアントは自分の行を購読して待合室 UI を表示し、承認された
  瞬間に自動入場する（ポーリング・リロード不要）。待合室でも表示名を変更できる。

- 管理者ロール（メンバーの承認・削除） ✅ **完了（2026-07-30、状態機械化

  状態機械で、**管理操作は状態遷移のみ・行は決して消さない**（誤操作は常に
  取り消せる）: `approve_member`（承認。誤拒否・誤バンからの復帰を兼ねる）/
  `reject_member`（申請の拒否・承認済みメンバーの追放。本人の明示操作で

  承認済み管理者であることをサーバー側で必ず検証し、account には一切触れない

  ガードレール）。管理パネルは承認待ち・メンバー・拒否済み・バン中の 4 区分＋

  リデューサーが不要なため。本番はモジュール publish 直後・URL 公開前に
  オーナーがサインイン+申請する運用で先取りを防ぐ — 採否理由は
  `initialMembership` のコメント参照）。管理者は操作対象にできない

- デプロイフロー（**全自動・人間のゲートなし**） ✅ **完了（2026-08-02）**:

- **スキーママイグレーション運用**（調査済み 2026-07）: Phase 1 以降は永続データを
  抱えるため `--delete-data` での再 publish は使えなくなる。再 publish 時の自動
  マイグレーションが受け入れるのは互換変更のみ — テーブル追加、**末尾への
  デフォルト値付きカラム追加**、インデックス/リデューサーの追加・削除など。
  カラムの型変更・削除・並べ替えは非互換で拒否される。運用ルール:
  ①スキーマ変更は原則追加（additive）で設計する ②非互換変更が避けられない場合は
  公式の**インクリメンタルマイグレーション**パターン（新テーブルを追加し
  リデューサーで段階移行）を使う ③本番 publish 前にステージング DB でリハーサル

  取れる見込み

  「入力なし かつ ウィンドウ起点のシミュレーションが静止 — 接地・速度ゼロ・

  までは空入力を送り続ける）。入力ガードは `startTick` 連続性前提を撤廃し、

  再設計（`evaluateInputBatch`）。オフライン掃除との相互作用は liveness の
  証明ごと再設計: 静止中は約2分毎の空 `submit_inputs` をハートビートとして

## Phase 3: 空間と会話グループ

**ゴール**: マップが複数になり、「会議」と「立ち話」が場所として成立する。

**増分分割（2026-08-04 決定、それぞれ独立 PR）**: ①複数マップ＋ポータル移動＋
AoI（map_id 列・購読絞り込みの採否） → ②会議室ゾーン（管理者設置・オープン/
クローズド） → ③立ち話グループ（その場発足・アバター追従・コソコソ演出） →
④チャットスコープ拡張（マップ/会話グループ、クローズドの RLS 可視性）＋
管理者の全体アナウンス。**①〜④すべて実装済み（2026-08-05）**。

- 複数マップ ＋ ポータル移動（移動摩擦のバランス設計はここで初検証）
  ✅ **実装済み（2026-08-04、増分①）**: マップはコード定義の `WorldMap`
  （`@kaede/shared` の map.ts — 物理ジオメトリ＋ポータル＋表示名。エディタは
  作らない）で、既存レベル＝「広場」（map 0）に「会議フロア」（map 1、幅半分の
  コンパクトなフロア）を追加。ポータルは MapleStory 流「中に立って ↑」
  （`detectPortalIntent` — up の押し始めエッジ・接地・ロープ非使用。ロープと
  同じ ↑ キーなので、トリガー域はロープ掴み範囲と重ねない — 共有ユニット
  テストで固定）。摩擦の初検証として広場側ポータルはスポーンから
  1,500px（徒歩約6秒）に置き、**行き先は相手側ポータルの中**に着地させる
  （帰り道は ↑ 一発 — 往路に摩擦・復路にショートカットという非対称を意図的に
  試す）。テレポートはリデューサー `enter_portal` の権威更新のみ（物理には
  入れない — マップ遷移を stepPlayer に入れると PlayerState に mapId が染みて
  予測・リプレイ全体が複雑化する）。クライアントは呼び出し前に保留入力を
  強制フラッシュ（`flushNow`）するため、決定論リプレイ後のサーバー行は
  クライアントの見ていた位置と正確に一致し、位置検証はスラックなしの同一
  幾何チェック（`evaluatePortalUse`）。着地姿勢は静止不動点（送信ゲートが即
  閉じられる — 共有ユニットテストで固定）。連打・敵対クライアント対策は
  トークンバケット（`portal_guard` — 持続1回/秒・バースト5。ポータル対は
  「着地点＝帰りのポータル内」なのでピンポン連打が常に幾何的に有効、かつ
  行更新は両マップの購読者への egress になるため）。E2E
  `map-travel.spec.ts` が「A の移動が B のブラウザから消える・後追いで
  合流できる・移動同期が移動先マップでも機能する・DM がマップを跨いで届く」
  を固定
- **購読の絞り込み（Area of Interest、段階方針を決定 2026-08-02）**
  ✅ **第一推奨（WHERE 絞り込み）まで採用・実装済み（2026-08-04、増分①）**:
  `player` に `mapId` 列（u32・**btree インデックス**・default 0 — 追加のみの
  変更で、旧スキーマ DB への再 publish 互換をローカルでリハーサル済み）を
  入れ、購読もマップ単位に絞った。購読は2クエリ構成: **自分の行は
  identity で**（どのマップに居ても ack とマップ変更通知が届く）、**他人の
  行は `WHERE mapId = 現在マップ`**（connection.ts の subscribeMapPlayers）。
  テレポート時は行き先マップを購読してから出発マップを解除（SDK の行
  参照カウントで自分の行はフリッカーしない）。採否の判断理由:
  ①実装で判明した本質は「player 行が**位置**（高頻度・マップ局所）と
  **在席**（低頻度・スペース全体）を兼ねていた」こと。位置購読を絞ると
  DM の宛先候補（スペース全体であるべき）が壊れるため、`player_name` に
  `online` 列を追加（additive）して**スペース全体の在席ディレクトリ**に
  昇格させ、DM 候補はそちらから読む（`collectDmCandidates` の入力は不変。
  online の書き込みはフラグが実際に反転する時だけで、行ダイエットは
  崩さない）。この「位置はマップ購読・在席はディレクトリ」の分離は後続
  増分（ゾーン・グループ・チャットスコープ）がそのまま乗れる形
  ②マップ切替で購読を張り替える機構は増分④のチャットのマップスコープ
  （`WHERE scope='map' AND target=現在マップ`）が同じものを必要とするので、
  チャット設計を待たずに採用してよい（「設計が揃う側に倒す」の判断）
  ③egress の支配項は移動中の行更新で、これがマップ内の人数に閉じる。
  name / status / reaction / chat の各テーブルは**全行購読のまま**
  （低頻度・小行で〜50人では絞る利益がなく、クローズドな会話の可視性制御は
  購読絞り込みではなく RLS の仕事 — dm_message の前例）。グリッドセル
  単位の細粒度 AoI は従来どおりやらない（SaaS 期の大規模テナントで再検討）
- **会議室ゾーン**: 管理者がマップ内に設置・編集。オープン/クローズド設定
  ✅ **「場所として成立する」まで実装済み(2026-08-04、増分②)**: 管理者による
  設置・編集(ランタイム行。マップ自体はコード定義のまま)、オープン/クローズド
  設定、ゾーンの描画(クローズドは 🔒+色違い)、在室判定と全クライアント同期
  (アバター下の 📍 タグ)。クローズドのチャット不可視(RLS)は増分④、立ち話は
  増分③。設計の要点:
  ①**スキーマは会話グループの統一抽象をそのままテーブル化**: `conversation_group`
  (公開。id u64 PK autoInc・kind・name・closed・mapId u32 **index**・x/y/w/h)+
  `group_member`(公開。identity PK → groupId u64 **btree index**)。増分③の
  立ち話は kind='huddle' の**行追加だけ**で同じ2テーブルに乗り(位置はメンバーの
  アバターから導出、設置列は使わない)、増分④のチャットスコープは kind を問わず
  groupId を target に参照し、クローズドの可視性は group_member への JOIN 1本の
  RLS フィルタで書ける(groupId のインデックスは RLS/購読フィルタ列の必須規則)。
  identity 主キーにより「同時に属せる会話グループは1つ」が構造で固定。
  kind は完全一致で絞る(未知の kind は描画されない — availability 語彙の前例)
  ②**入退室判定はサーバー側・権威位置の全 write path で実行**(受理バッチの
  決定論リプレイ直後・enter_portal 着地・join・ゾーン編集リデューサーの再判定)。
  **ポータルの前例(クライアント検出 → リデューサー → サーバー再検証)は不採用**。
  理由: (a) 判定コスト(PK lookup 1回+上限 ZONE_MAX=32 個の AABB テスト)は同じ
  呼び出し内の物理リプレイ(約24 tick)の誤差で、実行回数はアイドル抑制済みの
  受理バッチ数(移動中 2〜3回/秒/人・**静止中 0**)にしか乗らない — 「CPU 課金が
  入力レートに乗る」懸念は判定自体ではなく判定の置き場所の問題だった
  (b) クライアント発 enter/leave 方式は reducer call 自体が新規コスト
  (強制フラッシュ+呼び出しで実質2倍)な上、**leave を送らない敵対クライアントが
  ゾーン外からクローズド会話に居座る穴**(増分④で漏えい)を塞ぐために結局
  サーバー側の幾何バックストップが必須 — それなら最初からサーバー判定一本が
  単純で安全 (c) 境界に立ち続ける churn はサーバー側ヒステリシス(入室=素の
  矩形に中心、退室=ZONE_EXIT_MARGIN=32px 拡張矩形の外)で解消し、書き込みは
  遷移時のみ・反転には実移動(2×マージンの歩行)が要るため専用レート制限も不要
  ③**管理リデューサー**(create/update/move/delete_zone)はサーバー側 admin 検証
  (evaluateSettingChange — transitionMember の前例)。**設置座標はクライアントから
  受けない**: create/move は送信者の権威行の位置を中心にマップ境界へクランプ
  (位置の信頼問題が発生せず、管理 UI も「いまの場所に設置」ボタンで最小)。
  検証・幾何・ヒステリシスは `@kaede/shared` の zone.ts に置き単体テスト
  ④E2E `zone.spec.ts`(ゾーンを SQL シード — guest-admission の前例 — し、
  ゲスト2ブラウザで「入室 → 相手に 📍 同期 → 退室 → 消える → クローズド切替が
  描画に同期」を固定)。**旧スキーマ DB への再 publish をローカルでリハーサル済み**
  (スクラッチ DB に main のモジュール → join で行を入れ → 本ブランチを publish して
  受理・行存続・新テーブル作成・移行後 DB での在室判定と not-admin 拒否を実測)
- **立ち話グループ**: その場で発足、アバターに追従。オープン/クローズド設定。
  クローズドは「コソコソ話している」見た目の演出
  ✅ **実装済み(2026-08-05、増分③)**: 誰でも(ゲスト含む)その場で発足でき、
  オープン/クローズドを設定できる。クローズドは 🤫+紫の楕円の「コソコソ」
  演出(チャット不可視の RLS は増分④)。設計の要点:
  ①**スキーマは増分②の敷いたレールどおり行追加だけ**: kind='huddle' の
  conversation_group 行(設置列 x/y/w/h は 0 のまま未使用。位置はメンバーの
  アバターから毎フレーム導出し、描画の楕円がアバター群に追従する)。
  `mapId` は**発足マップで生涯不変** — ポータルで別マップへ跳ぶことは
  「歩き去り」と同じ退出。行の寿命はメンバー数: **0人になった瞬間に全
  削除経路(明示離脱・別グループへの移動・removePlayer)が行を掃除**する
  ので保持スイープ不要、かつ1 identity が生かせる立ち話は常に最大1つ
  (発足すると自分の membership が移って前の立ち話が死ぬ)— グループ上限
  ZONE_MAX(全 kind 共通)を独占できない
  ②**発足/参加/離脱はリデューサー**(create/join/leave_huddle)で、送信資格は
  チャットの前例(ワールド内 player 行+admission 再検証)+専用トークン
  バケット huddle_guard(公開行を書く呼び出しのため)。**発足位置は送信者の
  権威行から**(create_zone の規則 — クライアント座標は受けない)。参加は
  「近づいてボタン」UX: クライアントは共有 findJoinableHuddleId で候補を
  出すだけで、サーバーが evaluateHuddleJoin(同一マップ+最寄りメンバー
  から HUDDLE_JOIN_DISTANCE=140px)を権威行で再検証
  ③**歩き去りの自動離脱はゾーン在室判定と同じサーバー側占有パス**
  (syncGroupOccupancy — 旧 syncZoneOccupancy を kind 対応に拡張)に乗る:
  他メンバーの最寄り距離が HUDDLE_LEAVE_DISTANCE=320px 超(参加 140 との
  ギャップがヒステリシス — ゾーンの EXIT_MARGIN と同じ発想)かマップ違い
  で退出。ソロは距離判定なし(立ち話は発足者に追従して待てる)
  ④**会議室ゾーンとの関係は「明示の意図が幾何在室に優先」で確定**:
  ゾーン在室中でも発足/参加でき、identity 主キーの構造どおり membership が
  huddle へ移る。huddle 在籍中は占有パスがゾーン再入室を保留し(会議室に
  立ったまま立ち話しても会話が勝手に切り替わらない)、離脱すると**同一

- チャットスコープの拡張: マップ / 会話グループ（クローズドは非メンバーに不可視）
  ＋ 管理者機能: 全体アナウンス
  ✅ **実装済み(2026-08-05、増分④)**: 全体 / マップ / 会話グループ(zone・
  huddle を kind 問わず)でチャットを送り分けられ、クローズドな会話は
  非メンバーから**行ごと見えない**(RLS)。オープンな会話は周囲にも見える。
  管理者は全体アナウンスを送れる。設計の要点:
  ①**スキーマは増分②③が予告したとおり additive**: chat_message に
  `scope`(string・**btree index**・default 'space')+ `target`(u64・
  **btree index**・default 0。map は mapId をゼロ拡張、group は groupId、
  space は未使用)+ `announcement`(bool・default false)。既存行は
  全部「全体」として読める。**アナウンスを4つ目の scope 値にしなかった**
  のは、配送(RLS・購読・保持トリム)の観点では space と完全に同一で、
  違うのは送信資格と描画だけだから — scope 値にすると同じことを言うために
  3経路が分岐する
  ②**クローズドの可視性は RLS の許可集合**: フィルタを1本でも登録した
  瞬間、どのフィルタにも当たらない行は誰にも届かなくなるので、
  `scope='space'` / `scope='map'` / `scope='group' AND オープン
  (conversation_group への JOIN) / `scope='group' AND 自分が member
  (group_member への JOIN、`:sender`)の**4本で許可を明示**する。
  実装前スパイクで実測したこと(非オーナー接続2つ、2026-08-05):
  (a) JOIN を含むフィルタは通る (b) **JOIN を ON 句でなく WHERE で書くと、
  同じ表の購読が全部**「Subscriptions require indexes on join columns」で
  落ちる — `scope='space'` のような JOIN と無関係なクエリまで巻き添えになり、
  しかも publish は成功するので購読するまで気づけない (c) 既存の公開表に
  RLS を後付けしても旧行は space フィルタで見えたまま (d) closed の切替と
  membership の付与/剥奪は**ライブに反映**(付与で履歴が届き、剥奪で
  キャッシュから消える)。したがって代替案(配送行を作る等)は不要
  ③**closed はメッセージにスナップショットしない**: `conversation_group.closed`
  への live JOIN なので、会議中にクローズドへ切り替えれば履歴ごと隠れる。
  代償は「グループ行が消えた closed 行はどの JOIN にも当たらず全員から
  不可視になり、グローバル trim で自然消滅する」ことで、これは受け入れる
  (削除連動 cascade は書かない)。履歴はグローバル CHAT_HISTORY_MAX=100 の
  まま(per-scope cap・アナウンス除外は範囲外)
  ④**送信の権威はサーバー**: クライアントは scope と target を「名乗る」
  だけで、サーバーは自分の権威行から作った ChatContext に対して
  `resolveChatRoute` で検証する(マップ違いは wrong-map、属していない
  グループ ID は not-a-member — DM の「フォールバックせず送信エラー」の
  規則。宛先を勝手に読み替えない)。レート制限は chat_guard 共用(ChatPanel の
  ミラーが狂わないため)。アナウンスだけは chat_guard を**共用しない** —
  管理パネルから出る送信でミラーが知らないうちにバケットが減るため
  (reaction_guard の理屈)。専用バケットも置かない(admin ゲート済みで稀)
  ⑤**マップスコープは増分①の購読張り替え機構に相乗り**: `subscribeMapRows`
  (旧 subscribeMapPlayers)が player 行と `scope='map' AND target=現在マップ`
  を1つのハンドルで持ち、テレポート時は行き先を購読してから出発を解除する。
  chat_message の全表購読は廃止(space/group はスコープ別クエリで、group は
  RLS がさらに絞る)。**マップを離れると そのマップのログは購読解除で消える**
  — クライアント側バッファで擬似保持はせず、E2E で挙動として固定した。
  target が u64 なので map クエリだけは生 SQL(型付きビルダーのフィルタ値は
  string/number/boolean のみ)
  ⑥**E2E は wire 受信で主張する**: `groupChatRowsReceived`(dmRowsReceived の
  前例)を足し、クローズドな会話について「live 0 かつリロード後の seed も 0」
  → 参加すると届く(正例)→ 歩き去りで RLS が失効して消える、を
  `chat-scope.spec.ts` で固定。**旧スキーマ DB への再 publish をリハーサル済み**
  (main のモジュール → join+チャット行 → 本ブランチを publish → 移行計画は
  列3本と index 2本と RLS 4本の追加のみ・旧行存続・既定値 space/0/false・
  RLS 追加後も旧行が非オーナー接続に見える・移行後 DB での送受信と
  クローズド不可視まで実測)
  ⑦**アナウンスの検証は二分割**: 資格(管理者のみ・ゲスト不可)は
  evaluateSettingChange の単体テストと、実モジュールに対する非オーナー接続の
  拒否実測。配送(他マップ・クローズド在籍者にも届く／`[アナウンス]`+金枠の
  描画)は**admin ゲートを外したモジュールをスクラッチ DB に publish して**
  実測した — E2E で管理者を作れないため(member identity は Clerk サインインが
  必要で、space_member 行は timestamp 列を持ち `spacetimedb-cli sql` では
  INSERT できない)。E2E で管理者が要る機能が増えるなら、まずこの
  「テストから管理者を作る手段」を用意するのが先

**完了条件**: 会議室ゾーンでクローズドな会話ができ、外からは見えない。
立ち話グループを誰でもその場で作れる。
→ **達成(2026-08-05)**。Phase 3 の増分①〜④はすべて実装済み。

  ✅ **投入済み（2026-08-05）**: 色付き矩形を廃止し、AI 生成の簡易キャラ 1 種

  ②描画は**物理 AABB（32×48）の中心に高さフィットで載せるだけ**: 衝突・

  すべて AABB のまま — 見た目だけの変更で、E2E は snapshot フック

  ③facing 反転規約（`body.scale.x = facing`）は body を単位スケールの

## Phase 6: SaaS 化（構想段階）

ここは方向性のみ。Phase 4〜5 の運用実績を踏まえて具体化する。

- **スケール戦略: 不変条件2つのみ先行決定し、方式の本決定は本フェーズで行う
  （2026-08-02）**: SpacetimeDB は 1 データベース＝1 ノードの垂直スケールが
  基本で、水平シャーディングはない。方式の候補は「単一 DB＋`tenant_id`」
  「1組織=1DB のテナント分割」「規模によるハイブリッド」の3つだが、SaaS の
  実需要（テナント数・規模分布）が見える本フェーズまで確定しない。ただし
  後戻りが最も高くつくのは**スキーマに組織横断の構造が染み込むこと**なので、
  全フェーズ（Phase 2 のチャットスキーマ設計を含む）を拘束する不変条件を
  2つだけ今決める:
  ①**リアルタイム系テーブルに `tenant_id` 列や組織横断の構造を持ち込まない**
  （単一 DB＝単一組織スコープを保つ。現行スキーマは既にこの形で、購読クエリも
  `map_id` 等だけで済む）
  ②**組織横断データ（グローバルアカウント・持ち物・招待・横断集計）を
  org スコープの DB に置かない**
  この2つを守る限り、有力方向である **1組織=1DB**（組織境界がそのまま自然な
  分割線になり、線形スケール・障害/デプロイ/データ分離・テナント単位の
  原価計算＝エネルギー消費が付いてくる。テナント→DB の解決とトークン発行は
  コントロールプレーン＝Cloudflare Workers が担い、org DB にはグローバル
  アカウントの投影を持たせて Discord 型アカウントモデルと両立させる。
  **メンバーシップの真実源は各 org DB**（Clerk Org は課金/SSO のシェルとして
  必要時に後付け — 2026-08-04 確定、[ADR](./adr-auth-clerk-and-tenant-design.md)）。
  モジュールバージョン差異の管理は早期に自動化）への道は閉じない。
  単一 DB＋`tenant_id` はノード垂直限界が天井になり「他社のデータが見える」
  クラスのバグが構造的に残るため劣後、ハイブリッドは2系統のコードパスを
  永久に保守するため最劣後、という比較評価も本決定時の前提として残す
- 組織ごとの表示名/アバター上書き（プロフィールの漏出対策）
- エンタープライズ: SAML SSO / SCIM（退職時のオフボーディング統制）
- 招待 / 参加リクエストフロー（**第一候補はリンク招待** — Discord 式。URL の
  招待コードを `join_with_invite` リデューサーで検証する。メール基盤不要のまま。
  設計は [ADR](./adr-auth-clerk-and-tenant-design.md)。メール招待の実需が出たら
  Clerk の org 招待 — 無料枠込み — を検討）
- 管理者向けマップエディタ
- 通貨と課金（プラン連動で毎月配布＋追加購入。**Clerk Billing** を利用し、
  プラン状態は Webhook 中継で SpacetimeDB に同期 — VISION 参照）
- アカウントの本人削除フロー（Clerk のユーザー削除 Webhook → Worker 中継 →
  SpacetimeDB 側のデータ掃除）
- 英語対応（Paraglide に en ロケールを追加。翻訳の自動化として
  **Lingo.dev CLI** をこのタイミングで評価 — VISION の i18n 行を参照）
- モバイル対応
- `CallProvider` のコスト構造見直し（RealtimeKit 継続 or LiveKit/セルフホスト移行）
