  Discord 型の原則「アカウント（グローバルプロフィール）とスペースの
  メンバーシップを混ぜない」で設計。サインイン時に `account` を作成し、
  表示名は IdP のプロフィール名（JWT の `name` クレーム）で初期化

  `space_member` 行（公開テーブル）が `pending` になり、`join` をサーバー側で
  拒否。申請中クライアントは自分の行を購読して待合室 UI を表示し、承認された
  瞬間に自動入場する（ポーリング・リロード不要）。待合室でも表示名を変更できる。

- 管理者ロール（メンバーの承認・削除） ✅ **完了（2026-07-30、状態機械化

  状態機械で、**管理操作は状態遷移のみ・行は決して消さない**（誤操作は常に
  取り消せる）: `approve_member`（承認。誤拒否・誤バンからの復帰を兼ねる）/
  `reject_member`（申請の拒否・承認済みメンバーの追放。本人の明示操作で
  再申請可能 — 拒否直後に自動で申請列へ戻ることはない）/ `ban_member`
  （再申請を封じる）/ `unban_member`（バン解除 → rejected）。いずれも送信者が
  承認済み管理者であることをサーバー側で必ず検証し、account には一切触れない

  ガードレール）。管理パネルは承認待ち・メンバー・拒否済み・バン中の 4 区分＋

## Phase 2: プレゼンスとチャット

**ゴール**: 「一緒に作業している感」がテキストベースで成立する
（oVice の日常ユースの代替）。

- チャット: 全体スコープ ＋ @メンションの DM（マップ/グループスコープは
  Phase 3 で対象が生まれ次第拡張）
- 吹き出し表示
- リアクション（絵文字。アバター頭上に表示）
- ステータス手動切替（オンライン/離席/取り込み中）＋ 自由文ステータス
  （「もくもく作業中・話しかけてOK」等）。表示はまず名前横のアイコン/テキストで
  よい（アバターのポーズ表現は Phase 5）
- ブラウザ通知: バックグラウンドタブ中の @メンション・DM を通知する
  （常時つなぎっぱなし運用で DM が実際に機能するための前提条件）
- エラー監視の導入（**Sentry で確定**。無料枠で開始し、SaaS 期の利用分析
  （PostHog 等）導入時に再評価）
- チャットの乱用対策: 送信レート制限（Phase 0 の入力ガードと同様の考え方を
  チャットにも適用）。あわせて**ゲストに許可する行動範囲**（チャット可否・
  DM 可否・リアクション可否）をここで設計する
- チャット履歴の保持方針の設計（どこまで遡れるか、SpacetimeDB 上の保持量と
  古いメッセージの間引き）
- **プロトコルのアイドル抑制＋バッチ間隔延長**（コスト最重要レバー・試算済み
  2026-07、段階方針を複数案比較の上で決定 2026-08-02）:
  現行プロトコルは**静止中でも** 100ms ごとに入力バッチを送信し、行更新が全
  クライアントへ配信され続ける。ゲームデモでは無害だが、常時接続オフィスでは
  egress（2,000 TeV/GB ≒ $0.77/GB）が支配項になり、平均20人×8時間/日の接続で
  **月$300 級**になり得る。静止中は入力送信と行更新を止める（または大幅に間引く）
  設計変更を行う。`startTick` の連続性を前提とする入力ガードの再設計を含む。
  これを入れれば Maincloud Pro（$25/月、100,000 TeV 込み）圏内が現実的な見込み。
  **段階方針（2026-08-02）**:
  ①Phase 2 で実装するのは**アイドル抑制＋フラッシュ間隔の延長**
  （100ms → 300〜500ms、1呼び出しに複数 tick を同梱）。目標指標:
  移動中 2〜3 reducer calls/秒/人・静止中 0。実装前にこの数値で公式
  Pricing Calculator を通し、ドッグフーディングの実測（下記）と突き合わせる。
  オフィス用途は在席時間の 7〜8 割がアイドルのため、削減の大半はこの2つで
  取れる見込み
  ✅ **①実装済み（2026-08-02）**: フラッシュ間隔 100ms → 400ms（1呼び出しに
  約24 tick 同梱）＋送信ゲート（`@maple/shared` の `evaluateSendWindow`。
  「入力なし かつ ウィンドウ起点のシミュレーションが静止 — 接地・速度ゼロ・
  ロープ非使用 — かつ 送信済みが全 ack」のとき送信を完全に停止。静止到達
  までは空入力を送り続ける）。入力ガードは `startTick` 連続性前提を撤廃し、
  静止した行への `startTick` ギャップを「飛ばした空 tick」として受理する形へ
  再設計（`evaluateInputBatch`）。オフライン掃除との相互作用は liveness の
  証明ごと再設計: 静止中は約2分毎の空 `submit_inputs` をハートビートとして
  送り（スキーマ・リデューサー追加なし。専用 Web Worker で刻み、
  バックグラウンドタブのタイマー間引き — 従来は放置背景タブが掃除→再join→
  スポーンテレポートしていた — も同時に解消）、掃除自体（`sweepExpiredRows`・
  保持10分）は維持。リモート補間は INTERP_DELAY_MS 120→550ms・
  再送ウォッチドッグ 600→1200ms・INPUT_BATCH_MAX_TICKS 30→60 に整合。
  無操作の接続休止は 15分→60分へ延長（撤廃はしない — 休止が守るのは
  受信 egress と忘れタブ。判断の詳細は `idle.ts` のコメント）。
  実測（ローカル・Playwright 計測）: **移動中 2.4〜2.5 calls/秒・静止中 0**
  （ハートビートは約1本/2.3〜3.3分）で目標達成。公式料金表ベースの試算
  （20人×8h×30日・移動25%・reducer 呼び出し 840 TeV/百万・egress
  2,000 TeV/GB・行更新のワイヤサイズ 100〜150B と仮定）で月 5〜7.5万 TeV
  ≒ Pro 枠 100,000 TeV 内 — 従来プロトコル比で約 1/15〜1/20。
  ドッグフーディングの実測で最終検証する
  ②**変化点駆動（入力ビットフラグの変化時のみ送信）はエスカレーション先として
  温存**: 実測で Pro 枠に収まらない・余裕がない場合に限り実施する。移動中の
  呼び出しをさらに 1〜3回/秒へ落とせるが、リモート表示を「行更新の間を共有
  物理でクライアント側外挿する」方式へ変える再設計（補間・入力ガード・再同期）
  を伴い、デシンク系のリスクと検証コストが最大のため、実測前に確定させない。
  実施時の設計メモ: kaede は決定論物理＋ビットフラグ入力なので「変化点＋tick」
  だけで権威状態を完全再現でき、dead reckoning（速度外挿の近似）を使わず
  サーバー権威のまま実現できる。接続ライフサイクルのリファクタリング（下記）は
  この案を見据えた形にしておく
  ③**player 行のダイエットはどの案でも効く独立改善として Phase 2 で先行実施**:
  高頻度更新される player 行から、低頻度の `name` と、全クライアントに配る
  必要のないガード内部値 `allowanceMicros` を分離し、行更新1回あたりの egress
  を削る（egress・書き込み・読み取りの3メトリクスは行サイズに比例する）。
  非互換のスキーマ変更になるため、**実ユーザー投入前（＝ドッグフーディング
  開始前）のこのタイミングで行う**のがコスト最小
  ✅ **完了（2026-08-02）**: `name` は公開テーブル `player_name`（join/rename
  時のみ更新）、`allowanceMicros` は非公開テーブル `player_guard`（バッチ受理
  ごとに更新されるが非公開なので egress ゼロ）へ分離した。3テーブルは join で
  同一トランザクション生成・削除経路（`removePlayer`）で同時削除され、常に
  対になる。候補に挙がっていた `updatedAt` は分離しない — オフライン掃除用
  だけでなく、クライアントのリモート補間がサーバー時刻タイムラインの
  アンカーとして毎更新読んでおり（`remoteView.ts` のクロック推定）、行更新と
  同頻度で変わるため分離しても削減にならない。クライアントは初期購読に
  `player_name` を追加し、名前は行イベント＋キャッシュ参照で描画に接続
  **暫定ガード実装済み（2026-08-02）**: 無操作 15 分でクライアントが接続自体を
  休止し、次の操作で自動再接続する（`packages/client` の `net.package/idle.ts`。
  忘れられたタブの垂れ流し対策で、ステータス表示の AFK 検出とは別物）。
  アイドル抑制の実装時にこの休止時間の延長・撤廃を再検討する
  → ✅ **再検討済み（2026-08-02、アイドル抑制①と同時）**: 60 分へ延長して
  存続。あわせて、接続ライフサイクル（`net.package/sync.ts` の再試行・休止・
  世代管理）を純粋な状態遷移関数として切り出して単体テスト可能にする
  リファクタリングをこの再設計時に行う（2026-08-02 のコード品質レビュー
  指摘。暫定ガードの実装を先行させるため意図的に先送り）
  → ✅ **完了（2026-08-02）**: `net.package/lifecycle.ts` の `transition`
  （イベント → 次状態＋エフェクト列の純関数）に集約し、`sync.ts` は
  エフェクトを実行する薄いシェルに。変化点駆動へのエスカレーション時は
  接続状態機械に手を入れずに送信規則側を差し替えられる
- ドッグフーディング開始に伴う実測（**前提**: 実メンバーを入れる＝実ユーザー
  投入なので、開始前にドメイン取得 → Clerk 本番インスタンス作成 → issuer
  ゲート2件のクローズを済ませる — Phase 1 参照。開発インスタンスの Identity で
  実メンバーを入れると本番切替時に全アカウントの Identity 付け替えが必要になる
  ため）: Maincloud の利用料金（上記試算の検証。
  料金は $1≒2,592 TeV、egress 2,000 TeV/GB、ストレージ $1/GB/月、Free 枠は
  2,500 TeV/月で常用には不足＝Pro 前提）と日本からの RTT。問題があれば
  セルフホストを検討（VISION 参照）。エネルギーの内訳では **CPU 命令数**も
  確認する: kaede はコラボツールとしては例外的に座標をサーバー権威
  （決定論物理の再生）にしており、これは「詐称で得をする人がいないデータは
  クライアント権威でよい」という一般論（2026-08-02 資料レビュー）より重い
  選択。50人規模では許容の見込みだが、実測で CPU が支配項なら
  クライアント権威＋サーバー側クランプへの縮退を再検討する
- 後回し可: 無操作時の自動離席（AFK 検出）

**完了条件**: 常時つなぎっぱなしの「作業部屋」的な使い方が成立し、メンバー同士が
チャット・DM・リアクションで日常会話できる。

## Phase 3: 空間と会話グループ

**ゴール**: マップが複数になり、「会議」と「立ち話」が場所として成立する。

  インデックスを入れること — 追加のみの変更で、後から購読を絞る選択肢を
  保険として確保する。**第一推奨**は同時に購読クエリも `WHERE map_id = ...` で

## Phase 6: SaaS 化（構想段階）

ここは方向性のみ。Phase 4〜5 の運用実績を踏まえて具体化する。

- **スケール戦略: 不変条件2つのみ先行決定し、方式の本決定は本フェーズで行う
  （2026-08-02）**: SpacetimeDB は 1 データベース＝1 ノードの垂直スケールが
  基本で、水平シャーディングはない。方式の候補は「単一 DB＋`tenant_id`」
  「1組織=1DB のテナント分割」「規模によるハイブリッド」の3つだが、SaaS の
  実需要（テナント数・規模分布）が見える本フェーズまで確定しない。ただし
  後戻りが最も高くつくのは**スキーマに組織横断の構造が染み込むこと**なので、
  全フェーズ（Phase 2 のチャットスキーマ設計を含む）を拘束する不変条件を
  2つだけ今決める:
  ①**リアルタイム系テーブルに `tenant_id` 列や組織横断の構造を持ち込まない**
  （単一 DB＝単一組織スコープを保つ。現行スキーマは既にこの形で、購読クエリも
  `map_id` 等だけで済む）
  ②**組織横断データ（グローバルアカウント・持ち物・招待・横断集計）を
  org スコープの DB に置かない**
  この2つを守る限り、有力方向である **1組織=1DB**（組織境界がそのまま自然な
  分割線になり、線形スケール・障害/デプロイ/データ分離・テナント単位の
  原価計算＝エネルギー消費が付いてくる。テナント→DB の解決とトークン発行は
  コントロールプレーン＝Cloudflare Workers が担い、org DB にはグローバル
  アカウントの投影を持たせて Discord 型アカウントモデルと両立させる。
  モジュールバージョン差異の管理は早期に自動化）への道は閉じない。
  単一 DB＋`tenant_id` はノード垂直限界が天井になり「他社のデータが見える」
  クラスのバグが構造的に残るため劣後、ハイブリッドは2系統のコードパスを
  永久に保守するため最劣後、という比較評価も本決定時の前提として残す
- 組織ごとの表示名/アバター上書き（プロフィールの漏出対策）
- エンタープライズ: SAML SSO / SCIM（退職時のオフボーディング統制）
- 招待 / 参加リクエストフロー（**Clerk の招待機能を利用** — 招待メールも Clerk が
  送信するため自前実装・自前メール基盤は不要）
- 管理者向けマップエディタ
- 通貨と課金（プラン連動で毎月配布＋追加購入。**Clerk Billing** を利用し、
  プラン状態は Webhook 中継で SpacetimeDB に同期 — VISION 参照）
- アカウントの本人削除フロー（Clerk のユーザー削除 Webhook → Worker 中継 →
  SpacetimeDB 側のデータ掃除）
- 英語対応（Paraglide に en ロケールを追加。翻訳の自動化として
  **Lingo.dev CLI** をこのタイミングで評価 — VISION の i18n 行を参照）
- モバイル対応
- `CallProvider` のコスト構造見直し（RealtimeKit 継続 or LiveKit/セルフホスト移行）
