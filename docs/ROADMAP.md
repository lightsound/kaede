# kaede — ロードマップ

前提: [VISION.md](./VISION.md) を先に読むこと。**品質優先・締切なし**。フェーズは
依存関係に基づく順序であり、日付ではない。各フェーズの完了時（および方針変更時）に
本ファイルを PR で更新する。

**移行ライン（oVice からの引っ越し条件）**: ログイン ＋ 常設マップ ＋ チャット ＋
ステータス ＋ ビデオ通話（画面共有含む）。= **Phase 4 完了がコミュニティ移行の
マイルストーン**。

アートのワークストリーム（AI 生成×パーツ分割の検証）はフェーズに縛られず
**並行して**進めてよい。本格統合は Phase 5。**ただし Phase 4 の移行までに
「最低限のアバター」（着せ替えなしの簡易キャラ 1 種）を投入することを必達目標と
する** — コミュニティの第一印象を「色付き矩形」にしないため。

## Phase 0: ネットコード基盤 ✅ 完了

現リポジトリの状態。ゲーム MVP として作られたが、資産はそのまま次フェーズ以降の
土台になる。

- サーバー権威＋クライアント予測＋ reconciliation（決定論物理）
- ワンウェイ足場・すり抜け降下・ロープ
- 入力ガード（トークンバケット）、再接続レジリエンス、リモート補間
- 品質基盤: fallow 全53ルール error、単一 vitest ラン＋実測カバレッジ、CI での
  バインディングドリフト検査

## Phase 1: アイデンティティ基盤

**ゴール**: メンバーが複数デバイスから同じ名前・同じアバターで入れる。
メンバー以外は入れない。

- **最初のタスク: Clerk ↔ SpacetimeDB 接続スパイク**（JWT テンプレート＋issuer 登録
  →接続→再接続時のトークン再取得までを検証。実装に無理がある場合は
  フォールバック第一候補 **Kinde** で同スパイクをやり直し、VISION を更新）
- Clerk ＋ Google ログイン（既存の `sessionStorage` 匿名トークン方式を置換。
  再接続のたびに `getToken()` で新トークンを取得する。本番 Clerk インスタンスを
  実ユーザー投入前に確定させる — VISION の実装上の注意を参照）
- プロフィール（表示名）の永続化
- **承認制（待合室）**: 初回ログイン → 承認待ち状態 → 管理者が承認して入場可能に
- 管理者ロール（メンバーの承認・削除）
- ゲスト入場（ログインなしの一時アバター）と、その許可/不許可の設定
  （MVP では単一スペースのグローバル設定。将来の組織設定の原型）
- アカウントスキーマの土台: 内部 ID を主キーとする `account` テーブルに
  SpacetimeDB Identity をマッピング（認証プロバイダ変更時の再リンクに備える）。
  会話データを組織スコープに閉じる原則もこの時点のスキーマ設計から適用する
  （VISION のアカウントモデル・ガードレール参照）
- ホスティングの Vercel → Cloudflare 移行（Workers 静的アセット配信。
  **Alchemy v2 による IaC 化**（`infra/` に隔離、バージョンをピン留め）、
  `vercel.json` の置き換え、CI/デプロイ手順と README の更新まで含む。
  実ユーザー投入前に済ませる）
- **ドメインの取得**: **kaede.town で確定済み（2026-07-30）**。Cloudflare
  Registrar で取得し、Clerk 本番インスタンスをこのドメインで設定する
  （発行者＝Identity がこのドメインに紐づくため、以後変更不可 — VISION 参照）
- 環境戦略の確立: ローカル開発（SpacetimeDB local ＋ Clerk 開発インスタンス）と
  本番（Maincloud ＋ Clerk 本番インスタンス）の分離、環境変数・シークレットの
  整理（Cloudflare のシークレットは Alchemy / CI から注入）、
  ステージング環境の要否の判断
- **Stripe Projects のセットアップ（採用検証）**: `stripe projects` CLI で
  Clerk・Cloudflare・Sentry のプロビジョニング／リンクを試し、①既存アカウントへの
  リンク可否（特に Cloudflare — 新規開設フローしかない場合は Cloudflare のみ
  通常アカウント運用にする）②`.env` 同期と上記の環境戦略の整合、の2点を確認して
  正式採用を判断する（VISION「プロビジョニング・請求」参照）。前提:
  実行環境（Claude Code on the web）のネットワークポリシーで stripe.com /
  projects.dev への接続を許可しておくこと（2026-07-30 の初回トライは遮断されて
  いて実施不可だった）。`stripe login` のブラウザ承認のみ人間の操作が必要
- **バックアップ・復旧手段の確認**: Maincloud のバックアップ／エクスポート機能を
  調査し、恒久データ（アカウント・持ち物）の復旧手順を決めておく。
  スキーママイグレーション事故への保険でもあるため**実ユーザー投入前に必須**
- デプロイフロー（**全自動・人間のゲートなし**）: main マージで CI がクライアント
  （Alchemy）と SpacetimeDB モジュール（`spacetimedb-cli publish`）の両方を
  デプロイする。安全装置は自動チェックで担保する — 非互換スキーマ変更は publish
  自体が失敗して CI が止まり、既存のバインディングドリフト検査と E2E を
  デプロイの前段に置く
- **スキーママイグレーション運用**（調査済み 2026-07）: Phase 1 以降は永続データを
  抱えるため `--delete-data` での再 publish は使えなくなる。再 publish 時の自動
  マイグレーションが受け入れるのは互換変更のみ — テーブル追加、**末尾への
  デフォルト値付きカラム追加**、インデックス/リデューサーの追加・削除など。
  カラムの型変更・削除・並べ替えは非互換で拒否される。運用ルール:
  ①スキーマ変更は原則追加（additive）で設計する ②非互換変更が避けられない場合は
  公式の**インクリメンタルマイグレーション**パターン（新テーブルを追加し
  リデューサーで段階移行）を使う ③本番 publish 前にステージング DB でリハーサル
- **E2E スモークテストの導入（Playwright）**: Clerk スパイク完了後すぐ CI に
  組み込む。ローカル SpacetimeDB を CI 上で起動し、2 ブラウザで
  「ログイン→入場→移動同期→（Phase 2 以降）チャット」の基本シナリオを回す。
  vercel-labs/agent-browser は開発セッション中のエージェントによる動作確認・
  探索的 QA の補助ツールとして使い、CI には使わない（アサーション・fixture・
  トレースを持つテストランナーは Playwright が担う）。Cloudflare Browser
  Rendering は CI 用途には不向き（アプリも DB も CI 内 localhost にあるため）で、
  将来の本番死活監視で再検討
- 任意: パッケージ名の整理（`maple-like` / `@maple/*` → kaede 系へ改名。
  DB 名やデプロイ設定を触るこのタイミングが最小コスト）

**完了条件**: 2つのデバイスから同一アカウントで同じキャラクターを操作できる。
未承認ユーザーとゲスト不許可時の未ログインユーザーはワールドに入れない。

## Phase 2: プレゼンスとチャット

**ゴール**: 「一緒に作業している感」がテキストベースで成立する
（oVice の日常ユースの代替）。

- チャット: 全体スコープ ＋ @メンションの DM（マップ/グループスコープは
  Phase 3 で対象が生まれ次第拡張）
- 吹き出し表示
- リアクション（絵文字。アバター頭上に表示）
- ステータス手動切替（オンライン/離席/取り込み中）＋ 自由文ステータス
  （「もくもく作業中・話しかけてOK」等）。表示はまず名前横のアイコン/テキストで
  よい（アバターのポーズ表現は Phase 5）
- ブラウザ通知: バックグラウンドタブ中の @メンション・DM を通知する
  （常時つなぎっぱなし運用で DM が実際に機能するための前提条件）
- エラー監視の導入（**Sentry で確定**。無料枠で開始し、SaaS 期の利用分析
  （PostHog 等）導入時に再評価）
- チャットの乱用対策: 送信レート制限（Phase 0 の入力ガードと同様の考え方を
  チャットにも適用）。あわせて**ゲストに許可する行動範囲**（チャット可否・
  DM 可否・リアクション可否）をここで設計する
- チャット履歴の保持方針の設計（どこまで遡れるか、SpacetimeDB 上の保持量と
  古いメッセージの間引き）
- **プロトコルのアイドル抑制**（コスト最重要レバー・試算済み 2026-07）:
  現行プロトコルは**静止中でも** 100ms ごとに入力バッチを送信し、行更新が全
  クライアントへ配信され続ける。ゲームデモでは無害だが、常時接続オフィスでは
  egress（2,000 TeV/GB ≒ $0.77/GB）が支配項になり、平均20人×8時間/日の接続で
  **月$300 級**になり得る。静止中は入力送信と行更新を止める（または大幅に間引く）
  設計変更を行う。`startTick` の連続性を前提とする入力ガードの再設計を含む。
  これを入れれば Maincloud Pro（$25/月、100,000 TeV 込み）圏内が現実的な見込み
- ドッグフーディング開始に伴う実測: Maincloud の利用料金（上記試算の検証。
  料金は $1≒2,592 TeV、egress 2,000 TeV/GB、ストレージ $1/GB/月、Free 枠は
  2,500 TeV/月で常用には不足＝Pro 前提）と日本からの RTT。問題があれば
  セルフホストを検討（VISION 参照）
- 後回し可: 無操作時の自動離席（AFK 検出）

**完了条件**: 常時つなぎっぱなしの「作業部屋」的な使い方が成立し、メンバー同士が
チャット・DM・リアクションで日常会話できる。

## Phase 3: 空間と会話グループ

**ゴール**: マップが複数になり、「会議」と「立ち話」が場所として成立する。

- 複数マップ ＋ ポータル移動（移動摩擦のバランス設計はここで初検証）
- **会議室ゾーン**: 管理者がマップ内に設置・編集。オープン/クローズド設定
- **立ち話グループ**: その場で発足、アバターに追従。オープン/クローズド設定。
  クローズドは「コソコソ話している」見た目の演出
- チャットスコープの拡張: マップ / 会話グループ（クローズドは非メンバーに不可視）
- 管理者機能: 全体アナウンス

**完了条件**: 会議室ゾーンでクローズドな会話ができ、外からは見えない。
立ち話グループを誰でもその場で作れる。

## Phase 4: ビデオ通話 🚩 移行マイルストーン

**ゴール**: 会話グループ単位でビデオ通話・画面共有ができ、
**コミュニティが oVice を解約できる**。

- `CallProvider` アダプタの設計（Cloudflare RealtimeKit への直接依存を
  1 モジュールに閉じ込める。LiveKit 等への差し替え口を確保）
- 小さなサーバー API の新設（**Cloudflare Workers**）: RealtimeKit の参加トークン
  発行・録画開始/停止はシークレットキーを要するためブラウザから直接呼べない
  （SpacetimeDB モジュールも外部 HTTP を呼べない）。VISION の「バックエンドは
  薄いステートレスなグルーのみ」原則に従う
- 録画ファイルの R2 アーカイブ（録画完了 Webhook → R2 保存 → アプリから
  ダウンロード、の流れを設計）
- 会話グループ（会議室ゾーン/立ち話）単位の通話。ボタンで開始・参加する
  意図的なフロー（近接ボイスはやらない）
- 画面共有
- **録画 ＋ ダウンロード**（YouTube 等への二次利用が実際のユース）。
  方式は **RealtimeKit クラウド録画で決定**（$0.010/分。月10時間録画で約$6）。
  サーバー側合成のため録画者のタブに依存せず、録り直せない録画で事故らない。
  ベータ→GA の課金開始時期と録画ファイルの保存期間・取り出し方法は実装時に再確認
- 通話コストの実測とプラン判断（VISION の試算では RealtimeKit
  $0.002/参加者分 ≒ 月$20〜30想定）
- 録画の透明性: **録画中インジケータを通話参加者全員に表示**する（同意の前提）。
  録画ファイルへのアクセス権（誰が一覧・DL できるか）もここで設計する

**完了条件**: 会議室ゾーンで通話＋画面共有＋録画ができ、コミュニティの
oVice ユースケース一式（作業部屋/会議/画面共有/録画/ゲスト招待/チャット/DM/
リアクション）がすべて kaede で置き換わっている。あわせて、並行アート
ワークストリーム由来の**最低限のアバター**（矩形ではない簡易キャラ）が
投入済みであること。

## Phase 5: アバターと楽しさ

**ゴール**: 「Maple 風であること」が体験の核として機能する。
Gather/oVice に対する明確な差別化。

- パーツ分割アバターリグ（頭・胴・腕・脚・服レイヤー＋骨格アニメ）
- AI アート生成パイプラインの確立（スタイルガイド、パーツ規格、生成→取り込みの手順）
- ジェスチャー（ダンス・寝る・座る等）
- ステータスの視覚化（離席＝寝ているアバター、取り込み中＝ヘッドホン作業、
  AFK＝ウトウト）
- 着せ替え: 自分の部屋（お着替え）、服屋（服の入手）、床屋（髪型変更）。
  **MVP では通貨なし・全部無料開放**
- マップの見た目品質向上（タイル、パララックス背景）
- （検討）サウンド: 効果音・環境音・BGM（ON/OFF 切替前提）。Maple らしさの
  構成要素として評価する

**完了条件**: メンバーがアバターを自分好みにでき、ジェスチャーが日常の
コミュニケーションで使われている。

## Phase 6: SaaS 化（構想段階）

ここは方向性のみ。Phase 4〜5 の運用実績を踏まえて具体化する。

- マルチテナント（組織）と組織設定（ゲスト許可等を組織ごとに）
- 組織ごとの表示名/アバター上書き（プロフィールの漏出対策）
- エンタープライズ: SAML SSO / SCIM（退職時のオフボーディング統制）
- 招待 / 参加リクエストフロー（**Clerk の招待機能を利用** — 招待メールも Clerk が
  送信するため自前実装・自前メール基盤は不要）
- 管理者向けマップエディタ
- 通貨と課金（プラン連動で毎月配布＋追加購入。**Clerk Billing** を利用し、
  プラン状態は Webhook 中継で SpacetimeDB に同期 — VISION 参照）
- アカウントの本人削除フロー（Clerk のユーザー削除 Webhook → Worker 中継 →
  SpacetimeDB 側のデータ掃除）
- 英語対応（Paraglide に en ロケールを追加。翻訳の自動化として
  **Lingo.dev CLI** をこのタイミングで評価 — VISION の i18n 行を参照）
- モバイル対応
- `CallProvider` のコスト構造見直し（RealtimeKit 継続 or LiveKit/セルフホスト移行）
