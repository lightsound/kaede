# アバター アニメーション設計（Phase 5 — ポーズフレーム＋レイヤー合成）

状態: **方式確定（2026-08-08 オーナー承認）**。初版（パーツ回転リグ —
2026-08-07）はオーナー確認と議論を経て**全面転換**した（経緯は §1）。
実装増分への着手は、本方式でのスパイクやり直し→オーナー確認の後。
素材の規格・量産ライン・販売/UGC の不変条件は

## 1. 経緯 — なぜパーツ回転リグ（v1）を捨てたか

v1 は「頭・胴・腕・脚を別画像で持ち、PixiJS Container の階層で関節回転
させる」方式だった（スパイク PR #83 — クローズ済み。歩行は動いたが、
2 度の修正でも腕・脚の付き方の違和感が解消しなかった）。捨てた理由は
方式に構造的で、調整では直らないため:

1. **組み立てがボトルネック**: AI はパーツをバラバラに描き、組み立ては
   エージェントが目測で決めた座標数値。微妙な絵のずれを見抜く目が弱い
   エージェントが品質の律速になり、キャラを増やすたびに同じ調整が再発する
2. **棒の手足の回転では膝が曲がらない**: 「座る」「寝る」には曲がった脚の
   絵そのものが必要で、結局ポーズごとの絵を描き足すことになる — それなら
   最初からポーズ絵を正にする方が一貫する
3. **かわいさの天井が低い**: 硬い回転はロボット的。kaede はアバターの
   かわいさがプロダクト価値の核（オーナー 2026-08-08）

転換の決め手: 全身をポーズごと AI に描かせれば、**手足のずれは構造的に
発生せず**（AI は全身を一体で描く）、膝は曲がり、**体型を問わない**
（身長差・動物型もポーズシートを生成するだけ）。生成 AI の最も得意な
「全身を一体でかわいく描く」を品質の源にする — 同じキャラ 1 回の生成で
立ち・歩き 2 コマ・ジャンプ・座る・寝るの 6 ポーズが一貫して出ることは
実証済み（2026-08-08、ポーズシート実証画像 — 転換議論の PR 参照）。

## 2. 方式: ポーズフレーム＋レイヤー合成（MapleStory 本家の構造）

体はコマ絵、頭とアイテムはアンカー合成 — **本家 MapleStory と同じ
アーキテクチャ**（本家は体のコマ絵に neck/hand 等の取り付け座標を持たせ、
頭・髪・顔・装備を合成している）。

| レイヤー | 実体 | 着せ替え | 組み合わせの増え方 |
| --- | --- | --- | --- |
| 体（ポーズコマ） | ポーズごとの全身絵（コーデ込み） | コーデ単位で全身シートを差し替え | コーデ数 × ポーズ数（制作時に有界・QA 可能） |
| 頭グループ | 頭・髪・顔（表情）の 1 枚絵 | 髪・顔は 1 枚差し替え | **足し算**（髪 20 種 = 画像 20 枚） |
| 手持ちアイテム | 1 枚絵を hand アンカーに合成 | 差し替え | **足し算** |

- 描画は Pixi 本体機能の範囲（`AnimatedSprite` 相当のコマ切替＋Container
  合成）。外部アニメランタイムへの依存ゼロ。スプライトシート路線は Pixi
  公式度が最も高く（本体機能＋公式ツール AssetPack）、バッチが効くため
  〜50 人の同時表示にも最も強い（2026-08-08 外部調査の判断軸と一致）。
- チビキャラのコマは 2 倍解像度でも約 70×100px と小さく、VRAM は
  2048×2048 アトラス 1 枚（≈16MB）に 500 コマ以上入る — 「コマ×装備の
  爆発で VRAM が死ぬ」警告は装備をコマに焼き込む場合の話で、レイヤー
  合成では到達しない。

### 手法比較（v1 議論＋外部調査 2026-08-08 の要点）

| 手法 | 採否 | 理由の要点 |
| --- | --- | --- |
| 自前パーツ回転リグ | ✕（v1 で実証の上棄却） | §1。「オーサリングツールを自作する羽目になる」（外部調査）— 目測数値の調整がまさにそれだった |
| **ポーズフレーム＋レイヤー合成** | **採用** | 本節。専任アニメーター不在＋AI 生成という kaede の条件で最良。素材のロックインも最小 |
| Spine（公式 `spine-pixi-v8`） | 保留（DP-A の移行先） | skins は着せ替えと 1:1 だが、リグ・アニメ制作が GUI 手作業（体型ごと）でエージェント全自動と相性が悪く、パーツ絵の生成問題（v1 と同型）が残る。メッシュ変形・IK は Professional 版が必要、**年商 50 万 USD 超で Enterprise 必須**、エディタ⇄ランタイムの major.minor 一致必須。v8 で一次サポートが生きる唯一の外部アニメランタイムであることは移行先としての安全材料 |
| DragonBones | ✕ | 上流停止。新規採用は避ける（外部調査と一致） |
| Live2D / Rive / 3D(VRM) | ✕ | 立ち絵・UI 演出・3D 向き。全身横スクロールのチビキャラに不適合、Pixi 公式統合もない |

調査時の注意: 旧 `pixi-spine` は Userland 降格済みの v7 世代。v8 の情報は
`@esotericsoftware/spine-pixi-v8` を参照する（世代混入に注意）。

## 3. ポーズ規約 v1

- **標準ポーズセット**: `stand` / `walk-a` / `walk-b`（将来 4 コマ化可）/
  `jump` / `sit` / `sleep` / `wave` …。増分①a は stand＋walk のみ、
  ジェスチャー増分で拡張（ポーズの追加＝シートに 1 枚足すだけ）。
- **コマごとのメタデータ**（manifest — asset-pipeline.md §2）:
  - `neck` アンカー: 頭グループの取り付け点（頭はポーズでほぼ不変のため、
    髪・顔の着せ替えがポーズ数に関係なく 1 枚絵で済む — 本規約の核心）
  - `hand` アンカー: 手持ちアイテムの取り付け点（ポーズ限定アイテム可）
  - 接地基準: 足元 = 物理 AABB 下端（+24）
- **向き**: 素材は右向き（3/4 ビュー）＝ `facing = 1`。左は反転のみ。
- **歩行の交互性（①a オーナーレビューで顕在化した未解決課題 2026-08-08）**:
  チビキャラの左右の手足は同色のため、逆足の接地コマは絵としてほぼ同一に
  なり、歩行サイクルが片足スキップに見える。①a 時点の生成・後処理では
  解決できなかった — (a) テキスト指示・鏡像指示・参照画像編集のいずれでも
  接地 2 コマが同相に収束（実測 3 回）(b) 取り込みラインでの機械陰影付与
  （遠い脚を暗く・近い脚を明るく — 本家 MapleStory の遠近規約の機械版）は
  交互性は出るが**品質不合格で棄却**（オーナーレビュー — 機械的な明暗が
  陰影として不自然）。解決は①b 冒頭の**生成モデル選定ベンチ**で行う
  （ROADMAP ①b — 本命は動画生成モデルからのフレーム抽出。動きの整合性は
  動画モデルの学習の中心で、脚の交互性が構造的に得られる）。
- **不変のもの**: 物理 AABB（32×48）が衝突と全オーバーレイ（名前・
  ステータス・📍・吹き出し・リアクション）のアンカーの権威。E2E
  スナップショット（位置・ラベル）も不変。

## 4. 描画設計

- **`AvatarView` の薄い境界**（外部調査 §7 の推奨を採用）: 描画側に
  `play(motion)` / `setSkin(parts)` / `update(dt)` 級のインターフェースを
  切り、ゲーム側はモーション ID とスロット構成だけを知る。将来 DP-A で
  Spine 等へ差し替えても呼び出し側が壊れない — ImportLint の境界規約とも
  一致する
- **歩行同期（v1 スパイクから流用）**: 「描画された位置の毎フレーム水平
  差分」から歩行位相を進め、位相がコマ番号を選ぶ。ローカル（予測）と
  リモート（Hermite 補間）に同一規則が適用でき、**追加の同期データなし・
  スキーマ/ネットコード不変**。不連続（テレポート）は速度しきい値で検出
  （単体テスト済みの `advanceWalk` — 関節角の写像だけがコマ選択に変わる）
- facing 反転は既存規約 `body.scale.x = facing` のまま。

## 5. 将来要件への適合

| 要件（オーナー 2026-08-07〜08） | 適合 |
| --- | --- |
| アバターの種類をたくさん | ◎ シートを量産ライン（asset-pipeline.md §4）で生成するだけ。リグ調整なし |
| 身長の高い・低い / 動物型 | ◎ 体型の骨組みをコードが知らない — どんなシルエットも同じ仕組み |

| 服の自由ミックス | 中期はコーデ単位で有界。本命化したら **DP-A** |
| 世界観の統一・販売・UGC | asset-pipeline.md（規格・ファクトリー・不変条件）が担う |

## 6. 決定ポイント

- **DP-A 服の自由ミックス**（実施トリガー: コーデ単位では表現要求に
  足りなくなったとき）: 選択肢は 2 つ — (a) **服レイヤー化**（服もポーズ
  ごとの絵にして体コマへ合成 — MapleStory 完全準拠。体ポーズに合った服絵の
  生成・切り出しパイプラインの確立が必要で研究的要素あり。失敗しても
  コーデ単位に留まるだけで出荷済み機能は壊れない）/(b) **Spine skins へ
  移行**（§2 比較表の脚注を判断材料に。`AvatarView` 境界により呼び出し側は
  無傷、素材のポーズシートは参照ポーズ・パーツ素材として流用可）
- 配信の R2 移行・マーケットプレイスは asset-pipeline.md の DP-1/DP-2。

## 7. スキーマ影響（増分対応 — オーナー判断に上げる項目）

ポーズフレーム基盤＋歩行（①a）とファクトリー（①b）は**スキーマ・
ネットコード完全不変**。以降:

| 増分 | 必要になるもの | 設計方向（叩き台） |
| --- | --- | --- |
| ①c ジェスチャー＋ステータス視覚化 | ジェスチャー発動の同期 | reaction の前例（identity PK の upsert 公開行＋専用ガード・行イベント駆動）。ステータス視覚化は既存 `player_status` 行からの導出で追加なし |
| ①d 頭グループ（髪・顔）着せ替え | 選択の永続化 | `player_name` 系の低頻度公開行（在席ディレクトリの前例）＋ account への永続化 |
| ①e コーデ着せ替え＋持ち物 | 装備・持ち物 | **安定 ID を参照する** account スコープの持ち物（asset-pipeline.md §5 の不変条件。販売の土台） |
