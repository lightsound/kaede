## 1. 目的と背景

- VISION 技術方針（アート行）: **AI 生成、パーツ分割方式** — 頭・胴・腕・脚・服を
  別レイヤーで持ち骨格アニメで動かす。着せ替え×ジェスチャーの**組み合わせ爆発を
  回避**する。
- 実需シグナル（2026-08-07 ドッグフーディング）: 「アバターの種類をたくさん」
  「手や足も動いてほしい（歩行アニメーション）」。
- 後続依存: Phase 4.5 増分⑦の「座る」はこのリグが前提、⑦①装飾アセットは
  本パイプラインに乗せる（確立前の場当たり制作を避ける — PR #81 の裁定）。

## 2. リグ方式（決定案）

**PixiJS Container 階層＋パーツ回転/オフセットのプロシージャルアニメ**を採る。
スプライトシート切り替えは不採用、ただし将来の併用は妨げない。

### 2.0 手法の全体比較（2026-08-07 追補 — オーナー質問への回答）

PixiJS 本体に骨格アニメ機能は**ない**。2D キャラアニメの選択肢と採否:

| 手法 | 概要 | 採否と理由 |
| --- | --- | --- |
| **自前の Container 階層＋関節回転**（採用） | Pixi の標準機能だけで組む古典的ペーパードール。関節数が少ない単純リグの一般的な手法 | パイプライン全体（AI 生成 → 取り込み → リグ定義 → アニメ）が**コードとして再現可能**で、エージェント主体の開発方針（VISION）にそのまま乗る。依存ゼロ・全部単体テスト可能。代償: キーフレームはコードで書く＝アニメの品質はチューニング次第（本スパイクの初版の見た目の粗さは方式ではなくアセット比率・ジョイント座標・重なり順の調整不足 — §6.1） |
| **Spine**（`@esotericsoftware/spine-pixi-v8` — 公式ランタイム） | 2D 骨格アニメの**業界標準**。エディタで リグ・メッシュ変形・IK・物理・アニメブレンドを作り、ランタイムが再生。**skins 機能は着せ替えのための機構そのもの** | 不採用（現時点）。理由: ①リグとアニメの制作が **GUI エディタ作業**（有償ライセンス・人間の手作業）になり、「AI がパーツを生成 → エージェントが取り込む」という再現可能パイプラインが切れる ②エディタ⇄ランタイムのバージョン結合が強い（メジャー・マイナー一致必須）③kaede に必要なのは関節 6 個の回転だけで、メッシュ変形・IK は過剰。**再訪トリガー**: ジェスチャー・着せ替えの表現要求がコード製キーフレームの品質限界を超えたとき（その場合もパーツ規格・グリーンバック生成手順はそのまま Spine のアタッチメント素材に流用できる — 損失はリグ定義とアニメ関数のみ） |
| **DragonBones** | 無償エディタ＋ランタイム。Pixi v8 対応は第三者ランタイム（`dragonbones-pixijs`、週 77 DL） | 不採用。エディタは事実上開発停止、v8 ランタイムはコミュニティ製で採用実績が僅少 — ベータ採用の最低条件（ピン留めで安定して動く実績）を満たさない |
| **スプライトシート切替**（`AnimatedSprite`） | Pixi ネイティブの最も一般的なアニメ手法。フレーム画像を並べて再生 | 不採用（§2 本文）。着せ替え×アニメの直積でシートが爆発し、VISION の狙いと正面衝突。装飾オブジェクト等**着せ替えのない**アニメには今後も普通に使ってよい |
| **Live2D 等** | 高品位のメッシュ変形系 | 不採用。横スクロールのチビキャラに過剰で、制作もエディタ依存 |

まとめ: 「Container 階層＋回転」は Pixi における単純ペーパードールの
一般的な組み方で、リッチなリグの業界標準は Spine。kaede は**制作
パイプラインの再現可能性**（エージェントが素材からアニメまで全部作れる）を
優先して自前リグを採り、Spine は品質要求が超えた時のエスケープハッチとして
明記しておく。

- **階層**: 既存の `body`（単位スケール Container — facing 反転 `body.scale.x =
  facing` の既存規約はそのまま）の中に figure Container を置き、その子に
  パーツ Sprite を重ねる。各 Sprite はジョイント位置にアンカーを置き、
  回転がそのまま関節スイングになる。
- **アニメはコードのキーフレーム（純関数）**: 歩行は位相 → 各関節角の写像
  （`rig.ts` の `walkPose` — 単体テスト済み）。ジェスチャーも同形の
  「クリップ＝時間 → ポーズの純関数」で足す（①b）。
- **スプライトシート切替を採らない理由**: シートはアニメ×着せ替えの直積で
  枚数が爆発する（N 服 × M アニメの再生成）。リグならパーツ画像は服・髪
  1 種につき 1 枚で、全アニメがそのまま適用される — これが VISION の
  「組み合わせ爆発の回避」の実装形。
- **併用の余地**: 関節回転で表現できない変形（マント・スカートのなびき等）が
  必要になったパーツに限り、パーツ単位のフレーム差し替え（テクスチャ交換）を
  同じジョイントに載せられる。リグ構造は変えずに済む。

## 3. パーツ規格

座標系は**物理 AABB（32×48）の中心を原点とする論理 px**。AABB は衝突と
全オーバーレイ（名前・ステータス・📍・吹き出し・リアクション）のアンカーの
権威のままで、リグは「その箱がどう見えるか」だけを決める（Phase 4
「最低限のアバター」の規約を継承）。アセットは**表示解像度の 2 倍**で持ち、
Sprite スケール 0.5 で描画する（同前例）。

### パーツ一覧（v2 — オーナー指摘の修正後。§6.1 参照）

| パーツ | 命名 | 2x px（実測） | アンカー | ジョイント（論理 px） | 意味 |
| --- | --- | --- | --- | --- | --- |
| 頭 | `head` | 68×60 | (0.5, 0.9) | (0, +3) | ピボット＝首。髪先が AABB 上端 −24 に届き、顎（+6）が胴と袖の付け根を覆う（チビ頭身） |
| 胴 | `torso` | 30×30 | (0.5, 0) | (0, +3) | 首から腰まで（シャツ＋ベルト＋腰） |
| 腕 | `arm` | 8×20 | (0.5, 0.12) | (±5.5, +6.5) | ピボット＝肩（顎の下に隠れる）。近側/遠側で同一テクスチャを共用 |
| 脚 | `leg` | 15×22 | (0.5, 0.12) | (±3, +14.8) | ピボット＝股関節。**靴込みのチビ比率**で足先が AABB 下端 +24 に接地 |

- **レイヤー順（奥→手前）**: `armFar` → `legFar` → `torso` → `legNear` →
  `armNear` → `head`。**頭が最前面** — 巨大な頭が肩の継ぎ目を覆い、腕は
  「頭の下から生える」チビの見え方になる（v1 は近腕を頭より手前に置いて
  腕が頬に被さって見えた — §6.1 の修正①）。
- **遠側の腕・脚は同一テクスチャの tint 減光**（0xc9cbd4 — 弱め）で奥行きを
  出す。画像を 2 枚持たない。強い減光・青寄りの tint は表示サイズでは
  「灰色の浮遊物」に見える（v1 の 0xb0b6c4 から実測で修正）。
- **リグ定義は宣言的なブループリント**: パーツごとの（テクスチャ・アンカー・
  ジョイント座標・ポーズチャネル・遠側フラグ）を並べた 1 つの配列
  （`partsAvatar.ts` の `BLUEPRINT`）で、描画コードはそれを解釈するだけ。
  ①c のキャラ追加はブループリント＋パーツ画像の追加で済む形。
- **向き**: 素材は右向き（半横向き 3/4）で描く＝ `facing = 1`。左向きは
  既存規約どおり `body.scale.x = -1` の反転のみ。
- **着せ替えの乗り方（Phase 5 後半）**: 服は `torso` と同じジョイント・
  アンカーの追加レイヤー、髪は `head` の追加レイヤーとして**同じ関節に
  重ねる**。パーツ規格（アンカー・サイズ・レイヤー順）を守る限り、
  リグとアニメは無変更で着せ替わる。
- **⑦オブジェクトへの適用**: 装飾オブジェクトは「関節なしの 1 パーツ」として
  同じ規格（2x 解像度・論理 px 配置・グリーンバック生成 → 取り込み）に乗る。

## 4. AI 生成 → 取り込み手順

Phase 4「最低限のアバター」の前例（グリーンバック生成 → クロマキー透過 →
表示解像度の 2 倍に縮小 → Vite src import）を**パーツ単位に拡張**した。
再現手順:

1. **生成**: 既存キャラ画像を参照画像に渡し、**2×2 グリッドのパーツシート**を
   グリーンバック（#00FF00）で生成する。配置は 左上=頭 / 右上=胴 /
   左下=腕 / 右下=脚。プロンプト要点: パーツ同士を離す・切断面はフラット・
   腕と脚は垂直に伸ばした姿勢・背景に影を落とさない・文字やグリッド線を
   入れない（スパイクで使った全文は PR 参照）。
2. **取り込み**: `python3 scripts/import-avatar-parts.py <シート.png> <出力先>` —
   クロマキー（緑優勢 d = g − max(r,b) のソフト帯 20〜60 で透過、despill で
   緑被り除去）→ 象限ごとに切り出し・トリム → パーツ別の規格高さ
   （head 60 / torso 30 / arm 20 / leg 22 px）へ LANCZOS 縮小。
3. **配置**: `packages/client/src/game.package/avatar/` に置き、Vite の
   src import で同梱（ハッシュ付き配信）。

### スタイルガイド（生成プロンプトの共通条項）

- **頭身**: チビ 2 頭身。頭が全高の約 6 割（表示 48px 中、頭 ≈28px）。
- **手足はチビ比率で明示する（v1 の失敗からの必須条項）**: 腕・脚は
  「短い・ずんぐり（stubby/chunky）・胴と同程度の長さ」と明示し、脚は
  **大きな靴**（脚の高さの半分程度・キャラの向く方向に突き出す）を必ず
  含める。指定しないとモデルは大人比率の細長い手足を描き、規格高さへの
  縮小で靴・手のディテールが潰れて「棒」になる（§6.1 の修正③）。
- **視点**: 半横向き（3/4 ビュー）・右向き。
- **線と塗り**: くっきりした濃色アウトライン＋ソフトなセルシェーディング
  （MapleStory / 既存アバター準拠）。
- **パレット**: 既存キャラ＝茶髪・白シャツ・紺ズボン。新キャラも彩度・明度の
  レンジを既存キャラに合わせる（画面上で浮かない）。
- **禁止事項**: 背景への影・文字・枠線・パーツの重なり。

## 5. 歩行アニメと同期設計

**歩行/静止は描画層で導出し、同期データを一切足さない**（第一候補案を採用）。

- **導出規則**: 各プレイヤービューの「**描画された root 位置の毎フレーム水平
  差分**」から歩行位相と強度を進める（`rig.ts` の `advanceWalk`）。
  - 位相: 移動 64px で 1 歩行周期（歩幅が実移動と構造的に同期する）。
  - 強度: 実効速度 30px/s 以上で 1 へ、未満で 0 へ、時定数 90ms でイージング
    （歩き始め/止まりで関節が滑らかに遷移）。
  - テレポート耐性: **速度しきい値**（480px/s — 正当な移動の上限
    MOVE_SPEED 240 の 2 倍）を超えるフレームは不連続（ポータル・補正
    スナップ）とみなし、歩幅も歩行判定も進めない。距離の固定クランプは
    不採用: ラグの長フレームでは正当な歩行が数 tick 分まとめて届くため、
    距離で切ると歩幅が止まり実効速度も静止側に誤読される（Bugbot 指摘
    → 単体テストで仕様固定）。
- **ローカルとリモートが同一規則**: ローカルは予測補間後の位置、リモートは
  Hermite 補間（`remoteView.ts`）後の位置に同じ関数を適用するだけ。
  リモートの行データ（`vx` 等）にも触れないため、**ネットコード・スキーマ・
  E2E スナップショットは完全に不変**（E2E 全 21 件が無変更で通過 — 実測）。
- **既知の粗さ（①a で仕上げる項目）**:
  - 空中（ジャンプ・ロープ）でも水平移動中は脚が振れる。ローカルは
    `onGround`、リモートは行の `onGround` 列（同期済み・現在は描画未使用）で
    ジャンプポーズに差し替え可能 — 描画層の変更だけで足せる。
  - ロープ昇降（垂直移動）は現状スイングなし＝静止ポーズ。登りポーズは
    ジェスチャー機構（①b）のクリップとして足すのが自然。

### 6.1 オーナー確認での指摘と修正（2026-08-07 — v1 → v2）

初版（v1）の動画確認でオーナーから 3 点の指摘を受け、いずれも**方式では
なくアセットとリグ定数の調整不足**として同日修正した。見た目の変更は
オーナー確認が完了条件（Phase 4.5 の規約）— 修正版の動画・画像は
スパイク PR に添付:

1. **腕の位置ずれ**: 肩ジョイントが高すぎ（+6）、チビ頭身の巨大な頭の顎
   （+6）と同じ高さに袖が来ていた。肩を +6.5 に下げ、**袖の付け根が顎の
   下に隠れる**配置に修正（腕は頭の下から生える — チビの正しい見え方）
2. **重なり順**: v1 は近腕を最前面（頭より手前）に描いており、スイングの
   たびに腕が頬に被さった。**頭を最前面**へ修正（§3 レイヤー順）
3. **足が見えない**: 意図ではなくアセット欠陥。AI が大人比率の細長い脚
   （靴込み高さ 300px）を生成し、規格 20px への縮小で靴が潰れて棒になって
   いた。**チビ比率の手足（大きな靴）をプロンプトで明示**して再生成し、
   スタイルガイドに必須条項として追記（§4）。あわせて遠側 tint を弱めて
   「灰色の浮遊物」に見える問題も修正（§3）

## 7. スキーマ影響（オーナー判断に上げる項目）

リグ基盤＋歩行（①a）は**スキーマ・ネットコード完全不変**。以降の増分は
次のスキーマ追加（いずれも additive）が必要になる見込み:

| 増分 | 必要になるもの | 設計方向（叩き台） |
| --- | --- | --- |
| ①b ジェスチャー | 発動の同期 | reaction の前例（identity PK の upsert 公開行＋専用ガード）。行イベント駆動・seed 非表示 |
| ①c 種類追加 | アバター選択の永続化 | `player_name` 系の低頻度公開行（在席ディレクトリの前例）＋ account への永続化 |
| ①d ステータス視覚化 | なし | 既存 `player_status` 行から導出（描画のみ） |
| ①e 着せ替え | 装備・持ち物 | account スコープ（組織を跨いで持ち歩ける — VISION ガードレール）。詳細は着手時に設計議論 |

増分の分割と順序は [ROADMAP Phase 5](./ROADMAP.md) を参照。
