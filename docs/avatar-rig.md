# アバター アニメーション設計（Phase 5 — ポーズフレーム＋レイヤー合成）

状態: **方式確定（2026-08-08 オーナー承認）**。初版（パーツ回転リグ —
2026-08-07）はオーナー確認と議論を経て**全面転換**した（経緯は §1）。
実装増分への着手は、本方式でのスパイクやり直し→オーナー確認の後。
素材の規格・量産ライン・販売/UGC の不変条件は
[docs/asset-pipeline.md](./asset-pipeline.md)、増分の分割は

## 1. 経緯 — なぜパーツ回転リグ（v1）を捨てたか

v1 は「頭・胴・腕・脚を別画像で持ち、PixiJS Container の階層で関節回転
させる」方式だった（スパイク PR #83 — クローズ済み。歩行は動いたが、
2 度の修正でも腕・脚の付き方の違和感が解消しなかった）。捨てた理由は
方式に構造的で、調整では直らないため:

1. **組み立てがボトルネック**: AI はパーツをバラバラに描き、組み立ては
   エージェントが目測で決めた座標数値。微妙な絵のずれを見抜く目が弱い
   エージェントが品質の律速になり、キャラを増やすたびに同じ調整が再発する
2. **棒の手足の回転では膝が曲がらない**: 「座る」「寝る」には曲がった脚の
   絵そのものが必要で、結局ポーズごとの絵を描き足すことになる — それなら
   最初からポーズ絵を正にする方が一貫する
3. **かわいさの天井が低い**: 硬い回転はロボット的。kaede はアバターの
   かわいさがプロダクト価値の核（オーナー 2026-08-08）

転換の決め手: 全身をポーズごと AI に描かせれば、**手足のずれは構造的に
発生せず**（AI は全身を一体で描く）、膝は曲がり、**体型を問わない**
（身長差・動物型もポーズシートを生成するだけ）。生成 AI の最も得意な
「全身を一体でかわいく描く」を品質の源にする — 同じキャラ 1 回の生成で
立ち・歩き 2 コマ・ジャンプ・座る・寝るの 6 ポーズが一貫して出ることは
実証済み（2026-08-08、ポーズシート実証画像 — 転換議論の PR 参照）。

## 2. 方式: ポーズフレーム＋レイヤー合成（MapleStory 本家の構造）

体はコマ絵、頭とアイテムはアンカー合成 — **本家 MapleStory と同じ
アーキテクチャ**（本家は体のコマ絵に neck/hand 等の取り付け座標を持たせ、
頭・髪・顔・装備を合成している）。

| レイヤー | 実体 | 着せ替え | 組み合わせの増え方 |
| --- | --- | --- | --- |
| 体（ポーズコマ） | ポーズごとの全身絵（コーデ込み） | コーデ単位で全身シートを差し替え | コーデ数 × ポーズ数（制作時に有界・QA 可能） |
| 頭グループ | 頭・髪・顔（表情）の 1 枚絵 | 髪・顔は 1 枚差し替え | **足し算**（髪 20 種 = 画像 20 枚） |
| 手持ちアイテム | 1 枚絵を hand アンカーに合成 | 差し替え | **足し算** |

- 描画は Pixi 本体機能の範囲（`AnimatedSprite` 相当のコマ切替＋Container
  合成）。外部アニメランタイムへの依存ゼロ。スプライトシート路線は Pixi
  公式度が最も高く（本体機能＋公式ツール AssetPack）、バッチが効くため
  〜50 人の同時表示にも最も強い（2026-08-08 外部調査の判断軸と一致）。
- チビキャラのコマは 2 倍解像度でも約 70×100px と小さく、VRAM は
  2048×2048 アトラス 1 枚（≈16MB）に 500 コマ以上入る — 「コマ×装備の
  爆発で VRAM が死ぬ」警告は装備をコマに焼き込む場合の話で、レイヤー
  合成では到達しない。

### 手法比較（v1 議論＋外部調査 2026-08-08 の要点）

| 手法 | 採否 | 理由の要点 |
| --- | --- | --- |
| 自前パーツ回転リグ | ✕（v1 で実証の上棄却） | §1。「オーサリングツールを自作する羽目になる」（外部調査）— 目測数値の調整がまさにそれだった |
| **ポーズフレーム＋レイヤー合成** | **採用** | 本節。専任アニメーター不在＋AI 生成という kaede の条件で最良。素材のロックインも最小 |
| Spine（公式 `spine-pixi-v8`） | 保留（DP-A の移行先・ベイク経路は §6 DP-B） | skins は着せ替えと 1:1 だが、パーツ絵の生成問題（v1 と同型）が残る。制作の自動化は CLI＋スケルトン JSON のコード起点で可能と再評価（2026-08-08 — ライセンス費もオーナー了承済み）だが、変形が新しい絵を生まない素材トポロジーの問題は不変 → ベイク型の再評価条件は DP-B。エディタ⇄ランタイムの major.minor 一致必須。v8 で一次サポートが生きる唯一の外部アニメランタイムであることは移行先としての安全材料 |
| DragonBones | ✕ | 上流停止。新規採用は避ける（外部調査と一致） |
| Live2D / Rive / 3D(VRM) | ✕ | 立ち絵・UI 演出・3D 向き。全身横スクロールのチビキャラに不適合、Pixi 公式統合もない |

調査時の注意: 旧 `pixi-spine` は Userland 降格済みの v7 世代。v8 の情報は
`@esotericsoftware/spine-pixi-v8` を参照する（世代混入に注意）。

## 3. ポーズ規約 v1

- **標準ポーズセット**: `stand` / `walk-a` / `walk-b`（将来 4 コマ化可）/
  `jump` / `sit` / `sleep` / `wave` …。増分①a は stand＋walk のみ、
  ジェスチャー増分で拡張（ポーズの追加＝シートに 1 枚足すだけ）。
- **コマごとのメタデータ**（manifest — asset-pipeline.md §2）:
  - `neck` アンカー: 頭グループの取り付け点（頭はポーズでほぼ不変のため、
    髪・顔の着せ替えがポーズ数に関係なく 1 枚絵で済む — 本規約の核心）
  - `hand` アンカー: 手持ちアイテムの取り付け点（ポーズ限定アイテム可）
  - 接地基準: 足元 = 物理 AABB 下端（+24）
- **向き**: 素材は右向き（3/4 ビュー）＝ `facing = 1`。左は反転のみ。
- **歩行の交互性（①a オーナーレビューで顕在化した未解決課題 2026-08-08）**:
  チビキャラの左右の手足は同色のため、逆足の接地コマは絵としてほぼ同一に
  なり、歩行サイクルが片足スキップに見える。①a 時点の生成・後処理では
  解決できなかった — (a) テキスト指示・鏡像指示・参照画像編集のいずれでも
  接地 2 コマが同相に収束（実測 3 回）(b) 取り込みラインでの機械陰影付与
  （遠い脚を暗く・近い脚を明るく — 本家 MapleStory の遠近規約の機械版）は
  交互性は出るが**品質不合格で棄却**（オーナーレビュー — 機械的な明暗が
  陰影として不自然）。解決は①b 冒頭の**生成モデル選定ベンチ**で行う
  （ROADMAP ①b — 本命は動画生成モデルからのフレーム抽出。動きの整合性は
  動画モデルの学習の中心で、脚の交互性が構造的に得られる）。
- **不変のもの**: 物理 AABB（32×48）が衝突と全オーバーレイ（名前・
  ステータス・📍・吹き出し・リアクション）のアンカーの権威。E2E
  スナップショット（位置・ラベル）も不変。

## 4. 描画設計

- **`AvatarView` の薄い境界**（外部調査 §7 の推奨を採用）: 描画側に
  `play(motion)` / `setSkin(parts)` / `update(dt)` 級のインターフェースを
  切り、ゲーム側はモーション ID とスロット構成だけを知る。将来 DP-A で
  Spine 等へ差し替えても呼び出し側が壊れない — ImportLint の境界規約とも
  一致する
- **歩行同期（v1 スパイクから流用）**: 「描画された位置の毎フレーム水平
  差分」から歩行位相を進め、位相がコマ番号を選ぶ。ローカル（予測）と
  リモート（Hermite 補間）に同一規則が適用でき、**追加の同期データなし・
  スキーマ/ネットコード不変**。不連続（テレポート）は速度しきい値で検出
  （単体テスト済みの `advanceWalk` — 関節角の写像だけがコマ選択に変わる）
- facing 反転は既存規約 `body.scale.x = facing` のまま。

## 6. 決定ポイント

- **DP-A 服の自由ミックス**（実施トリガー: コーデ単位では表現要求に
  足りなくなったとき）: 選択肢は 2 つ — (a) **服レイヤー化**（服もポーズ
  ごとの絵にして体コマへ合成 — MapleStory 完全準拠。体ポーズに合った服絵の
  生成・切り出しパイプラインの確立が必要で研究的要素あり。失敗しても
  コーデ単位に留まるだけで出荷済み機能は壊れない）/(b) **Spine skins へ
  移行**（§2 比較表の脚注を判断材料に。`AvatarView` 境界により呼び出し側は
  無傷、素材のポーズシートは参照ポーズ・パーツ素材として流用可）
- **DP-B ベイク型リグ経路**（2026-08-08 新設 — オーナーとの外部案レビューで
  Rive MCP・Spine ベイク・Blender ベイクを統合評価した帰結）: リグ＋
  モーションカーブでポーズを作り、スプライトシートへ**ベイクして現ラインに
  取り込む**経路（ランタイム・アセット形式は不変）。実装候補は Blender
  ヘッドレス（bpy — 完全自動化可）/ Spine CLI（コード起点のスケルトン
  JSON。ライセンス費はオーナー了承済みで障害ではない）/ Rive MCP（公式
  MCP は Win/Mac デスクトップエディタ限定 — Linux のクラウドエージェント
  では動かない。ヘッドレスはコミュニティ製 MCP で供給元の検証が必要）。
  **強み**: 決定性（生成ガチャなし）・モーションの全キャラ使い回し
  （ポーズ数×体型数が足し算になる）・完全ループ・精密制御。**弱み**:
  変形は新しい絵を生まない（膝上げで見える靴裏・布のしわ・髪の揺れは
  ポーズごとの描き直しが必要で、そこは生成系の独壇場 — v1 棄却理由の本体は
  ツールの自動化可能性ではなくこの素材トポロジーにある）。
  **実施トリガー**: ①c のダンス増分（複数コマ・完全ループ要求）で動画抽出の
  品質/歩留まりが不足したとき、または量産期にポーズ数×体型数の掛け算が
  生成・検品コストの支配項になったとき。①b の歩留まり実測がこの DP の
  判定材料になる。
  **オーナー問題提起と対決実験の予約（2026-08-09、①b(a)⑵ スパイク中の
  議論）**: 「AI エージェントの進化でリギングのコストが下がり精度が
  上がるなら、長期的に価値が高いのは骨格路線では？ v1 の失敗は実物の
  Spine/Blender を使わなかったせいでは？」— 切り分けの合意: v1 の失敗の
  うち**ツールで直る部分**（関節位置の目測・数値制御・プレビュー不在）は
  実物の Blender/Spine（スクリプト・MCP 経由）で確実に改善する。
  **ツールで直らない部分**は素材トポロジー（骨の回転は新しい絵を生まない）
  と、メッシュ変形・ウェイト調整という審美判断の濃い手作業（エージェントの
  最弱領域 — ⑵ スパイクで位置ズレ指摘が繰り返された実測どおり）。
  AI の進化曲線は生成側（動画モデル＝毎フレーム絵を描き直すアニメーター）
  にも同じだけ効いており、どちらが先に勝つかは予測不能 — よって**予測せずに
  済む設計を維持する**: 資産の正はエンジン非依存の PNG＋manifest
  （asset-pipeline.md §1）で、コマの製法（動画生成/ベイク）をランタイムは
  区別しない。**工場だけを差し替えられる**ため、今シート方式を選んでも
  ロックインは生じず、清書済みポーズシート・参照画像・アンカー実測値は
  将来の自動リギングの良質な入力素材として無駄にならない。
  **決定（オーナー方針「開発・運用コスト削減の長期最良を選ぶ」への回答）**:
  ①c のダンス増分で**対決実験を実施する** — (a) エージェントが Blender を
  ヘッドレス実操作（bpy）してこのキャラに骨を入れ、ループアニメ 1 本を
  シートへベイクして現行取り込みラインに流す (b) 同じお題を動画生成
  ラインでも作る (c) コスト・所要時間・エージェント成功率・見た目を並べて
  オーナー判定。骨格路線の本命は Blender（無料・bpy フルスクリプト。
  Spine は有償＋ヘッドレス自動化の窓口が弱い）。勝った側が①c 以降の
  工場になる（負けた側も条件が変われば再評価 — 本 DP の実施トリガーは
  存続）
  **✅ 対決実施・オーナー判定（2026-08-10、①c）: 動画生成ラインの勝ち**。
  ベイクは機械的には完走（完全ループ・色/頭部ドリフトゼロ・振り付け
  使い回し可 — 再現ツール `scripts/factory/spike_blender_bake.py`）した
  が、見た目が「紙人形」判定 — 単一パーツ腕の回転では袖の向きが破綻し
  肘が曲がらない（本 DP の予言「変形は新しい絵を生まない」の実測確認。
  オーナー実見でも「服から手が飛び出す」）。①c 以降の工場は動画ライン。
  実施トリガー（品質不足・掛け算の支配項化）は存続。
  **追記 — 2026 年のツール地形（オーナーの「Blender 以外は？買えないか？」
  への調査回答、2026-08-10）**: ①2D リグツール（Spine/Live2D/Rive/
  Godot 2D ボーン）はメッシュ変形で紙人形感を緩和できるが、変形の設営
  （メッシュ・ウェイト）が審美的手作業そのもので、v1 棄却理由が再発する
  ②既製リグ済み 2D キャラ（$8〜15、Unity Asset Store 等）は**他人の
  絵柄**で、kaede の世界観統一・ファクトリー・UGC 構想（asset-pipeline
  §0）と両立しない。改変には Spine Pro ＋キャラごとの手作業が要る
  ③**本命は画像→3D 自動リギング（Tripo / Meshy 等、2026 現在）**:
  kaede の各キャラ画像から自動でリグ済み 3D モデルを生成し（Tripo:
  auto-rig 25 クレジット・リターゲット $0.10/モーション・プリセット
  100+、Meshy: プリセット 600+）、モーションを全キャラに使い回して
  レンダリング → 現行取り込みラインへ。ベイクの強み（決定論・完全
  ループ・使い回し）を紙人形問題なしで持つ可能性がある。**未知数は
  「3D レンダーが手描き 2D の絵柄を保てるか」**（CG 感のリスク —
  トゥーンシェーダ or AI リスタイル併用の要検証）。実施はオーナーの
  アカウント設営（Tripo/Meshy は AI Gateway カタログ外・BYOK 対象外）
  が前提のスパイクとして、本 DP の再評価トリガーに追加
  **✅ スパイク実施（2026-08-10、Tripo V3 — オーナー判定待ち）**:
  boy stand 原本から image-to-3D → auto-rig → dance プリセット 2 本の
  リターゲット → bpy 正投影エミッションレンダーまで**一発完走**
  （75 クレジット・~60 分。再現ツール `scripts/factory/spike_tripo_rig.py`
  / `spike_tripo_render.py`、コスト実測は factory-yield.md）。**成立した
  もの**: 形状忠実度（チビ頭身・髪・服が 3D でも保持）・紙人形問題の
  不在（脚交差・自由な腕ポーズ）・機械的な完全ループ（ポーズ署名の
  自己相似で周期発見、閉包 0.066 = walk 採用水準）・モーション使い回し
  の構造（rigged GLB は R2 保管済みで追加リターゲット 10 クレジット/本）。
  **未知数だった「絵柄の保持」の実測**: テクスチャが原画より暗く沈む
  （陰影ベイク）、96px でエッジが毎コマ煮える、**プリセット振付は演出
  指示不能**（dance_01/02 とも頭が下向きで顔が読めない — かわいさの
  主戦場である大きな顔が消える）。レンダーコマの nano リスタイルは
  ポーズドリフトで棄却（①b(c) の再実測）。videoReview 判定は動画レーン
  優位（補助 — 最終はオーナー目視）。判定材料（並列モンタージュ・
  並列ループ動画）は本スパイクの draft PR に添付
  **弱み対応ラウンド（同日追試 — オーナー問い「弱みは対応できないのか」
  への実証）**: ①色の沈み → 明度整合＋2D 原画 24 色パレットへの最近傍
  スナップで**解消**（決定論・キャラごと 1 回較正・副作用なし）②顔の
  下向き → プリセット**選定**がレバー（cheer は頭が上がり顔が読める。
  ただしループ有無・頭の向きは 10 クレジット/本の取り寄せガチャ）＋
  camera yaw 60 で可読性が video レーン水準へ接近 ③エッジの毎コマ煮え
  と squash & stretch の欠如（3D メッシュの剛体感）は**残存** — ここが
  動画レーンとの残差。入力画像は R2 原本 294×508（推奨 256² 超・
  単一視点）で、3D 化の形状忠実度は高く**入力起因の劣化ではない**
  （multi-view 追試の条件「単一視点で品質が出ない場合」は不成立）。
  **高解像度 A ポーズ入力での再走（同日・オーナー指示）**: nano で
  正面 A ポーズ 784×1355 を生成し 3D 化から再走 — モデルはよりクリーン
  になるが髪の彩度は依然原画比 −20%（Tripo のテクスチャ特性と確定）、
