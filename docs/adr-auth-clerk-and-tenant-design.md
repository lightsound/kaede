# ADR: 認証は Clerk を続投し、テナントの真実源は各 org DB に置く

- **ステータス**: **採用（2026-08-04 確定）** — オーナーとエージェントの議論
  （SpacetimeAuth・WorkOS との比較を含む）を経てオーナーが承認
- **対象**: kaede
- **最終更新**: 2026-08-04
- **やさしい解説（図解付き）**: [auth-architecture.md](./auth-architecture.md)

---

## 1. 決定

本 ADR は 2 つの決定を記録する。

1. **認証プロバイダは Clerk を続投する（役割は認証専任）。**
   SpacetimeAuth・WorkOS は不採用。決め手は issuer 主権（§4）。
2. **テナント（組織）の真実源は Clerk Organizations ではなく各 org DB に置く。**
   招待はリンク招待（Discord 式）、ban は二層分担、Clerk Org は将来の課金/SSO の
   シェルとして必要時に後付けする（§5）。

判断の時点で「乗り換えの費用が最安なのは今」（実ユーザー = オーナー 1 人のみ）で
あることを双方が認識したうえで、費用を無視してフラットに比較した結果である。

## 2. この判断が依存している前提

## 3. 唯一の不可逆点: issuer

SpacetimeDB の Identity は OIDC トークンの **iss + sub から決定的に導出**される。
実ユーザーがログインした後の issuer 変更 = 全ユーザーの Identity 移行。さらに
バックアップ・復旧手順（docs/backup-restore.md）の根幹 — 「DB が全損しても
Identity は issuer+subject から再導出される」 — もこの 1 点に依存する。

UI・組織機能・課金・SSO はあとから変えられるが、issuer は変えられない。
**したがって「issuer のドメインを誰が握るか」を支配的な判断基準とする。**

| 候補 | issuer | 主権 |
|---|---|---|
| Clerk（本番インスタンス作成済み） | `https://clerk.kaede.town` | **自分のドメイン・無料** |
| SpacetimeAuth | `https://auth.spacetimedb.com/oidc` | ベンダー固定・カスタムドメイン記述なし |
| WorkOS AuthKit | 既定 `authkit.app`。自ドメインは **$99/月** | 有料でのみ主権 |

Clerk は全プランでユーザー全量エクスポート（sub・パスワードハッシュ含む）が
可能なため、「自ドメイン issuer ＋ 全量エクスポート」の組み合わせで
**Identity を無傷に保ったままプロバイダを差し替えられる唯一の選択肢**になる
（脱出手順は §4.3）。

## 4. 決定 1: Clerk 続投（SpacetimeAuth・WorkOS 不採用）

### 4.1 SpacetimeAuth の評価（ドキュメント精読 2026-08-04）

事実（[公式 docs](https://spacetimedb.com/docs/core-concepts/authentication/spacetimeauth/)）:

- Maincloud に publish したモジュールのダッシュボードから有効化する
  **Maincloud 専用**のマネージド OIDC プロバイダ（ベータ）
- 認証手段: マジックリンク・Google・GitHub・Discord・Twitch・Kick・Steam。
  ログインページのテーマカスタマイズ、匿名認証トグル、ロール（ID トークンに
  クレーム同梱）。プロジェクトは DB から独立（dev/prod 分離可能）
- 管理はダッシュボード操作が前提（API/CLI は未文書化）
- 公式自身の位置づけ: 「サードパーティ OIDC ほど機能豊富ではない。高度な機能が
  要るならサードパーティを検討せよ」

**勝ち筋（本物）**: ベンダーが 1 社減る。dev/prod インスタンスの二重管理・JWT
テンプレート・pk_test/pk_live の配管・Clerk 用 DNS 5 レコードが全部消える。
匿名認証はゲスト文化と同思想（kaede のゲスト host トークンの issuer
`https://auth.spacetimedb.com` は既に `guestIssuers` に登録済みで、いわば親戚）。

**採らなかった理由**:

1. **issuer 主権がない（§3）**。ベータのバグは無視してよい（P5）が、これは
   バグではなく「復旧ランブックの前提を誰が握るか」の問題。SpacetimeAuth が
   （Maincloud は健在のまま）方針転換した場合、復旧は account テーブルの
   再リンク儀式になる — 〜50 人なら耐えられるが、無料で回避できるリスク
2. **SaaS へ進んだ場合、一番高くつく時期に移行する経路になる**。公式自身が
   高度な機能はサードパーティへと案内しており、エンタープライズ SSO・課金・
   組織まわりでいずれ移行が要る可能性が高い。Clerk なら移行は「永遠に不要」か
   「ドメイン差し替えで安価」のどちらか
3. ダッシュボード前提の管理は「管理操作もエージェント主体」（VISION 開発方針）
   と相性が悪い。Clerk は Backend API で実績済み（JWT テンプレート作成等）
4. UX も実は Clerk 側（アプリ内埋め込みコンポーネント vs ホスト型ページへの
   リダイレクト）

### 4.2 レイテンシについての整理（誤解の修正）

「SpacetimeAuth は Maincloud と同居しているのでレイテンシ ≒ 0 = UX 向上」という
仮説は成り立たない。認証のレイテンシが現れるのは ①サインイン時（支配項は
Google へのリダイレクト） ②再接続ごとのトークン取得（接続 1 回につき 1
リクエスト）のみで、いずれも「ユーザー操作 1 回級」の頻度。効くのは
**ブラウザ→認証サーバー**の距離であって、認証サーバー→DB の距離ではない
（SpacetimeDB は JWKS をキャッシュして署名検証するだけ）。Maincloud との同居は
むしろ「日本のブラウザから Maincloud と同じだけ遠い」ことを意味する。
**この軸では差がつかない（中立）。**

### 4.3 Clerk 続投の条件と脱出手順

続投には 3 条件を付ける（脱出可能性を口約束でなく構造にするため）:

1. **JWT テンプレートは標準クレーム最小構成を維持**する（Clerk 固有クレームに
   依存しない。現行: `aud: kaede-spacetimedb`・寿命 60 秒・`name` のみ）
2. **Clerk 依存は `auth.package` 隔離を維持**する（現状どおり）
3. **脱出手順を本 ADR に明文化**する（下記）

**脱出手順（Clerk と決別する日が来た場合）**:

1. Clerk からユーザー全量をエクスポートする（全プランで可能。user ID = `sub`、
   メール、OAuth 連携、パスワードハッシュを含む）
2. `clerk.kaede.town` の DNS（CNAME）を後継の OIDC プロバイダ（自ホストの
   Keycloak 等、または任意 issuer ドメイン＋任意 sub を許す SaaS）に向け、
   同 URL で OIDC ディスカバリ（`/.well-known/openid-configuration`）と JWKS を
   配信する
3. 後継プロバイダにユーザーをインポートし、**sub を旧 Clerk user ID のまま維持**
   してトークンを発行する
4. iss も sub も不変のため、**SpacetimeDB の Identity は全ユーザー無傷**。
   モジュール側の issuer 定数・クライアントの変更は不要（トークン取得の
   クライアント配線のみ差し替え）

この手順が成立するのは issuer が自分のドメインだからであり、§4.1 の判断の
裏返しになっている。

### 4.4 WorkOS AuthKit（オーナー判断で除外。理由を記録）

- 無料枠は最強（100 万 MAU、org・ロール・招待込み）で、エンタープライズ SSO
  （$125/接続/月）は本業。製品として劣る点はない
- 急所は **自ドメイン issuer が $99/月の有料アドオン**であること。実ユーザーの
  初ログインから issuer は固定されるため、初日から $99/月 を脱出保険料として
  払い続けるか、`authkit.app` に Identity を溶接するかの二択になる。Clerk は
  同じ保険が $0
- なお WorkOS の強み（エンタープライズ SSO）は今日選ばなくても失われない —
  §5.5 の「追加 issuer」経路で将来テナント単位に後付けできる

### 4.5 料金の現在地（2026-08 時点、判断の背景）

- Clerk: 無料 50,000 MRU。組織機能は全プランで 100 MRO・**1 org 20 人まで**・
  招待メール込み。21 人以上の org・参加申請（request to join）・カスタムロールは
  B2B アドオン（$100/月）。1 人 org は MRO カウント外
- kaede の当面の運用（オーナー確認済み）: コミュニティは 20 人以内＋ゲスト入場
  併用で無料枠内。課金は正式リリース時に判断

## 5. 決定 2: テナント設計 — 真実源は各 org DB

当初案（Clerk Org を真実源にし Webhook で投影）を議論の中で棄却し、反転させた。

### 5.1 テナント = 1 org DB。メンバーシップの真実源は DB 側

決定的な理由は P3: **モジュールは外部を読めないので、入場判定に使う
メンバーシップは結局その org DB に権威コピーとして置くしかない**。Clerk Org を
真実源にしても org DB への同期（Webhook 配線・ズレ検出・キック連動）を永久に
保守することになり、真実源が二重になるだけで得るものが「招待メール」程度しか
ない。現行の `space_member`（pending/approved/rejected/banned の状態機械、
行は消さない規約）をそのまま各 org DB の権威とする。**スキーマ変更ゼロ。**

### 5.2 招待はリンク招待（Discord 式）

URL の招待コード → サインイン → `join_with_invite` リデューサーがコードを検証
して membership を作る。メール送信基盤は不要のまま（VISION の「自前メール基盤を
持たない」と整合）。そもそも Discord がメール招待でなくリンク招待の文化で、
ゲスト入場と地続きの「気軽さ」にも合う。メール招待が必要になったら Clerk の
org 招待（無料枠込み）を検討する。

### 5.3 ban は二層分担

- **org 層**（あるスペースからの永久追放）: kaede 側（各 org DB）。Clerk に
  org 単位の ban は存在せず、Discord 型ガードレール（あるスペースの処分が
  グローバルアカウントを壊さない）からも org スコープであるべき。
  **リンク招待の導入で ban の価値はむしろ上がる**（有効なリンクを持つ元メンバー
  を join 時に弾くガードが必要 — 現行実装が既にその形）
- **プラットフォーム層**（サービス全体からの追放）: Clerk の user ban
  （Backend API、全セッション無効化）。SaaS 運営者だけが握るレバーで、自作不要

### 5.4 Clerk Org は課金/SSO のシェルとして必要時に後付け

Clerk Billing（org 単位サブスク）やエンタープライズ SSO を使う時点で、kaede org
と 1:1 の Clerk Org を Backend API で作る。**シェルに入れるのは支払い管理者
だけ**でよい（機能ゲートは Webhook → Worker → リデューサーでサーバー権威に
強制する既定方針のため、一般メンバーを Clerk Org に入れる必要がない）。帰結:

- 「1 org 20 人まで」の無料枠制限に実質当たらない
- 1 人シェル org は MRO カウント外（コスト ≒ 0）
- 課金開始時に Clerk Billing vs Stripe 直結を再評価する（§7）

### 5.5 トークン設計: org クレームは使わない

入場判定は Identity 対 `space_member` 行（現行実装と同じ）なので、トークンに
org クレームは不要。これにより「Clerk の active org はセッション単位でタブ間
共有される」問題（タブ A が org X の世界、タブ B が org Y の世界を開いた際の
再接続トークン取り違え）が**構造的に消滅**する。org → DB の解決はコントロール
プレーン（Workers）の公開ディレクトリで足り、認可は接続先の DB 自身が行う。
将来エンタープライズテナントが専用 IdP を求めたら、そのテナントの DB にだけ
別 issuer（WorkOS 等）を登録すればよい — `memberIssuersFor` は最初から
複数 issuer のリストであり、**認証プロバイダを 1 社に統一する必要はない**。

### 5.6 今から守る布石（実装は Phase 6 まで温存）

1. `initialMembership`（最初の申請者 = 管理者）は「org 作成者 = 初期管理者」に
   置き換わる前提を維持（docs/dogfooding.md の UX メモに既記載）
2. `space_member` は「投影に降格できる」形を保つ（現行の追加のみ設計で既に充足）
3. JWT テンプレートへの org クレーム追加は additive なので、必要になった時点で
   足せる（§4.3 条件 1 と両立）

## 6. 併記: 関連して同日に確定した事項

- **セルフホストの除外**（P2）: アイドル抑制（ROADMAP Phase 2 ①）の実装で
  コスト面の動機が消えたため、Maincloud 継続を確定。RTT に問題が出た場合は
  補間・プロトコル側の調整で吸収する
- **ドッグフーディングの URL 共有は保留**: オーナー自身の試用で、現状の機能
  セットでは常用に至らないと判明。作り込み（Phase 3 以降）を進めてから共有・
  実測を再開する（開始条件のゲート群はクローズ済みのまま有効 — ROADMAP Phase 2）

## 7. 判断が覆る条件（見直しトリガー）

1. **SaaS の芽を摘むと決めた**（P1 の変化）→ SpacetimeAuth の簡素さが優位に
   なり得る（その場合も issuer リスクは account 再リンク儀式で吸収できる規模か
   を確認すること）
2. **SpacetimeAuth がカスタムドメイン issuer と管理 API を提供した** → §3 の
   表が変わるため再評価
3. **Clerk の料金・エクスポート方針が変わった** → 脱出手順（§4.3）の実行可否を
   即確認。手順が生きているうちは判断不変、死んだら即時再評価
4. **エンタープライズ SSO の実需が来た** → WorkOS を「追加 issuer」として評価
   （§5.5 — 移行ではなく追加なので本 ADR の決定とは矛盾しない）
5. **課金を開始する** → Clerk Billing（シェル org 案）vs Stripe 直結を再評価
6. **メール招待の実需が出た** → Clerk org 招待の採用を検討（§5.2）

## 付録: 検討の経緯（推奨が変わった記録）

| 段階 | 推奨 | 変化の要因 |
|---|---|---|
| 初期 | Clerk Org をテナントの真実源に（Webhook 投影） | VISION の既定（Organizations が Clerk 選定理由）を素直に延長 |
| 再考 1 | **真実源を org DB に反転**・メール招待 → リンク招待 | P3（モジュールは外部を読めない → 権威コピー必須 → 真実源二重化は同期負債だけ残る）。リンク招待なら 20 人制限・MRO・request-to-join アドオンも回避 |
| 再考 2（オーナー要請でゼロベース比較） | Clerk 続投（消極的） | 「org を使わないなら Clerk の必要性が薄れる」との指摘に対し、残存価値を「自ドメイン issuer 無料・実装済み・Billing 選択肢・UI」と整理 |
| SpacetimeAuth 精読・WorkOS 事実確認後 | **Clerk 続投（確定）** | 判断軸を「唯一の不可逆点 = issuer の主権」に一本化。WorkOS は自ドメイン $99/月が急所でオーナーが除外。SpacetimeAuth はレイテンシ仮説の修正（§4.2）とセルフホスト除外（P2）を織り込んでも issuer 主権と SaaS 経路の非対称性で及ばず |
