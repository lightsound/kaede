# kaede — ビジョン

## 一言でいうと

**MapleStory 風の 2D 横スクロール世界を舞台にした、ワークコラボレーションツール（バーチャルオフィス）。**

Gather や oVice のように「同じ空間に人がいる感覚」を作るツールを、横スクロール
アクションの視点と物理で作る。ゲームを作るのではなく、ゲームライクな楽しさを持つ
仕事場を作る。

## 背景と狙い

- Gather・oVice・ZEP・SpatialChat 等の既存バーチャルオフィスは、すべて見下ろし型
  （トップダウン）か平面マップ型。**横スクロール型の常設ワークスペースは空白地帯**。
- 横スクロールには見下ろし型にない固有の強みがある:
  - **高さが意味を持つ**。フロア＝階層、ロープ＝階段、屋上＝休憩スペース、と
    オフィスビルのメタファーが空間構造と自然に一致する。
  - **移動そのものに感情表現が乗る**（ぴょんぴょん跳ねて挨拶する等）。偶発的な
    コミュニケーションの装置になる。
  - アバターの**着せ替え・ジェスチャー**という MapleStory 的な愛着要素が
    「そこに居たくなる理由」を作る。汎用ツールが失った部分。
- リスクとして自覚していること: 横スク物理は移動に摩擦を生む（人に近づくのに
  ジャンプやロープ操作が要る）。ポータル等のショートカットとの**バランス設計が
  このプロダクト最大の設計課題**。

## ターゲット

| フェーズ | ターゲット |
| --- | --- |
| MVP | 運営者の小規模コミュニティ（同時接続 最大〜50人）の**常設オフィス**。現在使用中の **oVice を置き換える**。Slack は併用を継続する（Slack 連携・Slack サインインは不要）。 |
| 将来 | ビジネス利用・イベント開催にも使える**汎用 SaaS** として展開。 |

## 体験の核

1. **物理は楽しさの源泉として残す**。ジャンプ・ロープ・重力・ワンウェイ足場は
   削らない。移動の摩擦はポータル/ワープ等のショートカットで緩和する。
2. **アバターが感情と状態を表現する**。着せ替え、ジェスチャー（ダンス・寝る等）、
   ステータスの視覚化（離席中＝寝ているアバター、取り込み中＝ヘッドホンをして
   作業しているアバター）。
3. **会話グループ**という統一抽象。
   - **会議室ゾーン**: マップ内の特定の場所に管理者が設置する（マップ移動はしない）。
   - **立ち話グループ**: 任意の場所でその場で発足し、アバターに追従する。
   - どちらも**オープン/クローズド**（周囲にチャットのやりとりが見えるか否か）を
     設定できる。クローズドの立ち話は周囲から「コソコソ話している」ように見える演出。
   - チャットのスコープも、ビデオ通話の単位も、この抽象に乗る。

## コミュニケーション方針

- **テキストが基本**: チャット（全体／マップ／会話グループ／@メンションの DM）＋
  吹き出し＋リアクション＋ステータス（手動切替＋自由文）。
- **ビデオ通話は意図的な開始**（ボタンクリック等）。「近づくと声が聞こえる」
  近接ボイスは当面やらない。**画面共有は MVP から必須**。録画→ダウンロードも
  コミュニティで実際に使われているため必要。
- 常時カメラ/マイクONの文化ではなく、「アバターを置いて一緒に作業している感」が
  日常のメインユース。

## 技術方針（決定事項）

| 項目 | 決定 | 補足 |
| --- | --- | --- |
| 同期基盤 | SpacetimeDB を継続 | サーバー権威＋クライアント予測のネットコード資産（Phase 0）をそのまま活かす。同期プロトコルは Phase 2 で**アイドル抑制＋バッチ間隔延長**（目標 移動中 2〜3 reducer calls/秒/人・静止中 0）を実装し、実測で Pro 枠に収まらない場合のみ**変化点駆動（意図ベース）**へ進む段階方針（2026-08-02）。購読は Phase 3 で `map_id` 列＋インデックスを必須とし、マップ単位の絞り込み（AoI）を第一推奨とする — 詳細は ROADMAP 参照 |
| 認証 | **Clerk**（Google ログイン中心） | SpacetimeDB は OIDC 準拠トークンを受けるため Clerk と公式に連携可能（[公式ガイドあり](https://spacetimedb.com/docs/core-concepts/authentication/Clerk/)）。SpacetimeAuth ではなく Clerk を選ぶ理由: Discord 型のコンシューマー体験（既製 UI・Organizations）と将来のエンタープライズ SSO への到達性。Phase 1 冒頭に接続スパイクを置き、実装に無理がある場合（エスケープハッチが必要になる等）のフォールバック第一候補は **Kinde**（同じく OIDC 準拠で issuer 登録の仕組みは同一。Organizations 込み、無料枠 10,500 MAU / 5 組織、有料は $25/月〜）。フォールバックの判断は**実ユーザー投入前に**行う（投入後のプロバイダ変更は Identity 移行になるため）。ゲストはトークンなし接続の一時 Identity。※SpacetimeDB の Identity は発行者＋ユーザーIDから導出されるため**プロバイダ変更はユーザー移行を伴う**。自前の `account` テーブルは内部IDを主キーにし Identity をマッピングする（再リンク可能にする）。実装上の注意: ①Clerk セッショントークンは短命なので**再接続のたびに `getToken()` で新しいトークンを取得**する（キャッシュ禁止） ②Clerk の開発インスタンスと本番インスタンスは発行者ドメインが異なり **Identity も別物になる**ため、実ユーザー投入前に本番インスタンスを確定させる ③JWT テンプレートで issuer/claims を固定し、その issuer を SpacetimeDB 側に登録する。**2026-08-04 再確認（確定）**: ピボット後の再検討（SpacetimeAuth・WorkOS との比較）を経て **Clerk 続投**。役割は**認証専任**とし、Org 機能はテナントの真実源にしない。決め手は issuer 主権（`clerk.kaede.town` ＋全量エクスポートによる「Identity 無傷の脱出経路」— 手順含め [ADR](./adr-auth-clerk-and-tenant-design.md) に記録）。続投条件 3 点（JWT テンプレート最小構成・`auth.package` 隔離・脱出手順の文書化）も同 ADR 参照 |
| アカウントモデル | **グローバルアカウント（Discord 型）＋組織メンバーシップ層** | アバター・持ち物はアカウントに宿る（組織を跨いで持ち歩ける）。設計ガードレール: ①会話データ（チャット・DM）は**組織スコープに閉じる** ②組織ごとの表示名/アバター上書きを後付けできるスキーマ ③OIDC 準拠で SAML/SCIM を後付け可能に。**テナント実装の設計は 2026-08-04 に確定**: テナント = 1 org DB（メンバーシップの真実源は各 org DB の `space_member`）・招待はリンク招待（Discord 式、メール基盤不要のまま）・ban は二層（org 層 = kaede、プラットフォーム層 = Clerk user ban）・Clerk Org は課金/SSO のシェルとして必要時に後付け — [ADR](./adr-auth-clerk-and-tenant-design.md) |
| 録画 | **RealtimeKit クラウド録画（実装済み 2026-08-06）** | GA 後 $0.010/分（映像。2026-08-06 時点はベータ無償・GA 後も月 100 分の無料枠）。サーバー側合成で信頼性が高く、録り直せない録画ユースに適合。LiveKit Egress（Ship $50/月〜、超過 $0.02/分）との比較でもこの規模では優位。録画 API の置き場所は UI Kit 本採用後の閉じ込め現実に従う: サーバー側（開始/停止・R2 直送）は `packages/server` の procedure（増分⑥で Worker から移設。Webhook 検証は D1 で廃止）、クライアント側（トグル・録画中インジケータ・一覧/DL UI）は `packages/client/src/call.package` の中だけ（増分①の `CallProvider` アダプタは増分③で撤去済み — ビデオ通話行を参照）。録画ファイルは Start Recording の `storage_config` で自前 R2 バケットへ**直接アップロード**し（プロバイダ側バケットの 7 日保持に依存しない）、一覧・ダウンロードは module の procedure（`list_recordings` / `recording_download_url`）が presigned URL で R2 を読む。権限・メタデータ・プリセットの決定は決定ログ 2026-08-06 と ROADMAP Phase 4 増分④⑥を参照 |
| メンバー管理 | 承認制（待合室方式） | 初回ログイン→承認待ち→管理者が承認。招待リンクは SaaS 化フェーズで追加 |
| ゲスト入場 | 組織設定で許可/不許可を切替 | ログインなしで一時アバターとして入場。oVice 同様の「気軽さ」の要 |
| ビデオ通話 | Cloudflare RealtimeKit（**UI Kit 本採用** — 2026-08-06） | 通話中 UI は RealtimeKit **UI Kit**（プリビルドコンポーネント）で組む。理由: デバイス設定・グリッド・参加者タイル等の会議アプリ的な要求が現時点で既にあり、自前実装で埋めるより安い（GA 予定価格 $0.002/参加者分も許容済み）。ベンダー閉じ込めは初期の「realtimekit.ts 1 ファイル」から「**`packages/client/src/call.package` 1 パッケージ**」へ緩和: UI Kit の import と meeting オブジェクトの流通は call.package の外に絶対に漏らさない（境界は ImportLint が強制）。将来の LiveKit 乗り換えは「UI Kit ごと差し替え＝call.package 書き直し」という**有界なコスト**として受け入れる（LiveKit にも `@livekit/components-react` という同型のプリビルド UI がある）。サーバー側の対（REST でミーティング作成・トークン発行・録画制御）は `packages/server/src/provider.ts` の 1 ファイル（増分⑥で Worker から module の procedure へ移設 — バックエンド行を参照） |
| アート | AI 生成、**ポーズフレーム＋レイヤー合成方式**（2026-08-08 改訂） | 体はポーズごとの全身コマ（本家 MapleStory と同じ構造）、頭・髪・顔・手持ちアイテムはコマのアンカーに合成するレイヤー。着せ替え×ジェスチャーの組み合わせ爆発は「頭・アイテムのレイヤー化（足し算）＋服はコーデ単位（有界）」で回避する。初版の「パーツ分割＋骨格アニメ」はスパイク実証の結果棄却（パーツをバラで生成して目測で組む工程が品質の律速・棒の手足では座る/寝るが作れない — [設計文書](./avatar-rig.md) §1）。アセットの正はエンジン非依存（PNG＋manifest）で、全アセット共通の規格・量産ファクトリー・世界観統一の機構・販売/UGC の不変条件は [asset-pipeline.md](./asset-pipeline.md) |
| クライアント | PC ブラウザ最優先 | モバイル最適化は当面度外視（既存のタッチ操作は壊さない程度） |
| ホスティング | **Cloudflare**（現在の Vercel から移行） | 判断理由: RealtimeKit と管理画面・請求を一元化、録画ファイルの R2 アーカイブ、原価販売のドメイン（Registrar）。性能面の注記: リアルタイム経路（ブラウザ↔SpacetimeDB の WebSocket、ブラウザ↔RealtimeKit の WebRTC）はどのみちホスティングを経由しないため、この選定は性能ではなく**エコシステム統合**の判断。体感を左右するのは**ブラウザ↔SpacetimeDB の RTT** で、Maincloud のリージョンに依存する（**セルフホストは 2026-08-04 に選択肢から除外** — アイドル抑制の実装でコスト面の動機が消えたため。RTT に問題が出た場合は補間・プロトコル側の調整で吸収する）。移行は実ユーザー投入前（Phase 1）に実施。静的配信は Pages ではなく **Workers の静的アセット配信**（Cloudflare の現行推奨）を使う。メール送信基盤は不要の見込み（認証系メールは Clerk が送信し、スペースへの招待はリンク招待でメール自体を使わない — 2026-08-04 確定、[ADR](./adr-auth-clerk-and-tenant-design.md)） |
| IaC | **Alchemy v2**（ベータ） | TypeScript ネイティブの IaC。全部 TS・型で縛るという本リポジトリの思想と一致し、Worker↔R2 等の型付きバインディングが得られる。ベータ採用の条件: ①バージョンを厳密にピン留めし、アップグレードは意図的なタスクとして実施 ②Alchemy/Effect のコードは `infra/` に隔離しアプリコードに漏らさない ③wrangler での手動デプロイという逃げ道を常に維持する。**IaC の範囲は Cloudflare リソースのみ**（Clerk・SpacetimeDB・PostHog は IaC 外だが、エージェントが MCP / CLI で操作する — 開発方針の「管理操作もエージェント主体」を参照） |
| プロビジョニング・請求 | **Stripe Projects**（projects.dev）**採用（2026-07-30 検証完了・確定）** | 外部サービス（Clerk・Cloudflare・PostHog 等 45+）のアカウント開設・API キー発行・請求を CLI から一括管理する Stripe のツール（2026-03 提供開始）。採用理由: ①「管理操作もエージェント主体」の方針にど真ん中で合致（エージェントがプロビジョニング〜支払いまで実行できる設計）②プロバイダごとに月 $100 の支出上限が API レベルで強制される（エージェント運用のコスト安全装置）③ツール自体は無料でサービス料金への上乗せなし、発行されるのは各サービスの通常の API キーなので**ロックインは実質なし**。役割分担: アカウント・キー・請求の層は Stripe Projects、Cloudflare アカウント内のリソース定義（Workers・R2・DNS）は Alchemy — 競合せず併用。**SpacetimeDB（Maincloud）は対象外**で従来どおり別管理。検証結果（2026-07-30、ROADMAP Phase 1 参照）: Cloudflare は**既存アカウントへの OAuth リンクに成功**（懸念だった新規開設強制はなし）。Clerk・Sentry は Projects 管理の新規アカウント作成方式（いずれも未セットアップだったため実害なし）。`.env` 自動同期と名前付き環境（`env create` / `env use`）が環境戦略と整合。留意点: Cloudflare のカタログに R2 はなく汎用 API トークンも発行されない（アカウント ID・workers.dev サブドメイン等のみ）ため、Alchemy 用の API トークンは従来どおり別途発行する — 上記の役割分担どおりで問題なし |
| エラー監視・ブラウザ観測 | **PostHog（2026-08-03 確定、Sentry から変更）** | 判断の全記録は [ADR](./adr-observability-posthog-over-sentry.md)。外部ベンダーはブラウザ側の PostHog 1 点に限定し、Workers は Cloudflare 純正（Workers Logs / Analytics Engine）、SpacetimeDB は Maincloud ダッシュボード＋ `spacetime logs` で観測する。決め手: ①外部ツールが必要な穴は「ブラウザの未捕捉例外」のみで、Sentry の Cloudflare/トレース統合は観測対象が存在しない ②無料枠の差（例外 100,000 vs 5,000、リプレイ 5,000 vs 50）③フィーチャーフラグ同梱（段階公開・kill switch）④SaaS 期の利用分析まで 1 ベンダーで賄える。既知のトレードオフ: グルーピング精度は Sentry 未満（手動 fingerprint で制御）、トレンドアラートは最短 hourly（ADR 追補参照） |
| ライセンス | **プロプライエタリ（全権利留保）** | LICENSE ファイルは置かない（デフォルトで全権利留保）。リポジトリは非公開運用を基本とし、OSS 化はしない。SaaS 収益化の方針と整合 |
| バックエンド | **外部境界は SpacetimeDB module の procedure に集約**（2026-08-06 改訂。Cloudflare Workers は静的配信のみ） | 状態は SpacetimeDB に一元化する。シークレットを要する外部 API 呼び出し（RealtimeKit ミーティング作成・トークン発行・録画制御、R2 一覧・presigned DL）は module の **procedure**（同期 outbound HTTP ＋ `ctx.withTx`）で行い、認証は SpacetimeDB 接続の `ctx.sender` がそのまま担う — 別系統の bearer 検証や Worker⇄module 信頼アンカーは持たない（ROADMAP Phase 4 増分⑤→⑥の経緯）。秘密は module の非公開テーブル（owner SQL で播種・**日次バックアップから除外**）。Workers に残る役割は静的アセット配信だけで、**常駐サーバーや独自 DB は作らない**は不変。将来の Webhook 受信（課金・Clerk ユーザー削除）は SDK の HTTP handlers（module 直受け）を第一候補として受け口ごと再設計する |
| スケール戦略（SaaS 期） | **不変条件2つを先行決定**（方式の本決定は Phase 6） | SpacetimeDB は 1 DB＝1 ノードの垂直スケールが基本。方式（単一 DB＋`tenant_id`／1組織=1DB／ハイブリッド）の確定は SaaS の実需要が見える Phase 6 まで遅延するが、後戻りが最も高くつく部分だけ不変条件として全フェーズを拘束する: ①リアルタイム系テーブルに `tenant_id` 等の組織横断構造を持ち込まない ②組織横断データ（グローバルアカウント・持ち物）を org スコープの DB に置かない。この2つを守る限り、有力方向の **1組織=1DB テナント分割**（組織境界＝自然な分割線。線形スケール・分離・テナント単位原価）への道は閉じない（候補比較と詳細は ROADMAP Phase 6） |
| 経済 | MVP は通貨なし・全部無料 | SaaS 化フェーズでプラン連動の通貨（毎月配布＋追加購入）を検討 |
| 課金（将来） | **Clerk Billing** | Stripe 手数料＋0.7%。プラン定義・組織単位サブスクリプション・機能ゲートが Clerk ダッシュボードで完結し、Stripe 側の設定が不要。プラン状態は Clerk の Webhook で SpacetimeDB に同期し、リデューサーがサーバー権威で強制する。受け口は module の HTTP handlers 直受けが第一候補（Clerk は svix HMAC 署名 — 純 TS HMAC を流用できる。バックエンド行と ROADMAP 増分⑥ D1 を参照） |
| i18n | **Paraglide JS（確定）** | メッセージをビルド時に型付き関数へコンパイルする方式。キーのタイポ・パラメータ不一致が TS コンパイルエラーで捕まり、React と PixiJS キャンバスの両方から同じ関数を呼べる（単一系統で管理）。MVP は ja のみで、UI 文字列のハードコード禁止を Phase 1 から適用。英語追加時（SaaS 化）には翻訳自動化層として **Lingo.dev CLI**（Paraglide のロケール JSON を LLM 翻訳。BYO-LLM 可）を評価する。Lingo.dev **Compiler** は JSX 専用でキャンバス側の文字列を扱えず管理が2系統に割れるため不採用 |
| E2E テスト | **Playwright を CI で** | ローカル SpacetimeDB を CI 上で起動して 2 ブラウザの同期シナリオを回す。vercel-labs/agent-browser は開発セッション中のエージェント QA 補助（CI には使わない）。Cloudflare Browser Rendering は CI 不向きで、将来の本番死活監視候補 |

## 開発方針

- **品質優先・締切なし**。フェーズは順序であり日付ではない。
- 開発体制はオーナー＋ Claude（AI エージェント）が中心。
- **ドキュメント駆動**: 方向性・設計判断は `docs/`（本ファイルと
  [`ROADMAP.md`](./ROADMAP.md)）に置き、PR で更新する。エージェントは
  セッション開始時にこの 2 ファイルを読むこと。
- 既存の品質基準（fallow 全ルール error、カバレッジ実測、境界強制）は維持する。
- **管理操作もエージェント主体**: 外部サービスの管理はダッシュボードの手動操作を
  最後の手段とし、エージェントが操作できる経路を優先して整備する。
  PostHog は公式ホスト型 MCP サーバー（`mcp.posthog.com` — エラー調査・フラグ操作・
  リプレイ検索・SQL）＋ CLI、Clerk は `@clerk/agent-toolkit`（ローカル MCP。
  ユーザー・組織の管理操作）＋公式 MCP（SDK スニペット参照）、Cloudflare は
  公式 MCP 群、SpacetimeDB は CLI（publish / logs / sql / energy）。
  やむを得ず手動操作した場合は設定内容を docs に記録する。
- デプロイは**全自動**（main マージ → CI がクライアントとモジュールの両方を
  デプロイ。人間のゲートなし。安全装置は CI の自動チェックで担保）。

## やらないこと

- **近接ボイス**（近づくと声が聞こえる）— 通話は意図的な開始のみ。将来の再検討は妨げない。
- **戦闘・モブ・XP 等のゲームプレイ要素** — PR #2 はこの方針転換によりクローズ済み。
- **モバイル最適化**（当面）。
- **Slack 連携・Slack サインイン**。
